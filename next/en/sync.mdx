For an existing database, start by reading its structure. `pull` inspects database catalogs and writes the representable structure as a Volan schema. With a schema already written, `push` plans a transition from the actual structure to the desired one and can apply it to a development database.

Both operations deal with tables and constraints. Client generation is separate: it reads the schema file, does not connect to a database and never runs push automatically.

## CLI

```bash
volan db push --schema schema.volan --url jdbc:sqlite:./data.db --dry-run
volan db push --schema schema.volan --url jdbc:sqlite:./data.db
volan db pull --url jdbc:sqlite:./data.db --stdout
```

CLI preview supports these commands independently of runtime generation. DATABASE_URL must be a JDBC URL. Push reads the datasource URL unless `--url` overrides it; pull uses DATABASE_URL or `--url`. For server databases set DATABASE_USER and DATABASE_PASSWORD through your environment or secret manager.

Pull prints with `--stdout` or creates `--schema introspected.volan`. Existing files require `--force`. Export uses env("DATABASE_URL"), not credentials. Preserve the original schema: pull cannot recover all client declarations.

## Library

Alpha.2 SQLite setup: add `volan-migrate` to the dependencies of [First query](/next/en/quickstart), aligned by the BOM.

```kotlin
import io.github.thirtyeighttwentysix.volan.ir.SchemaLoader
import io.github.thirtyeighttwentysix.volan.dialect.sqlite.SqliteDialect
import io.github.thirtyeighttwentysix.volan.migrate.DatabaseSync
import io.github.thirtyeighttwentysix.volan.migrate.SqliteReader
import java.nio.file.Files
import java.nio.file.Path
import java.sql.DriverManager

val schema = SchemaLoader.load("schema.volan",
    Files.readString(Path.of("schema.volan"))).schemaOrThrow()
val sync = DatabaseSync(SqliteReader(), SqliteDialect)
DriverManager.getConnection("jdbc:sqlite:./data.db").use { connection ->
    val plan = sync.plan(connection, schema)
    println(plan.toSql(SqliteDialect))
    sync.push(connection, schema)
}
```

Use dedicated JDBC connections beginning in auto-commit mode. Render and review the plan before applying; never auto-accept destructive changes from untrusted input. `sync.plan` is actual → desired; `sync.drift(connection, SchemaMapper.map(expectedSchema))` is expected → actual. These compare structure, not table data, and read only catalogue data.

## Safety and history

Warnings require explicit `--accept-data-loss`. A warning can indicate failure on existing rows as well as data loss. Renames are modeled as drop/add; use reviewed ALTER RENAME SQL to retain data.

PostgreSQL/SQLite push verifies structure before transaction commit. H2/MySQL/MariaDB can leave committed DDL and use a private `_volan_push` journal with [manual recovery](/next/en/migrations). A successful repeat is empty.

Push does not create migration files or append versioned history. Deploy reviewed [versioned migrations](/next/en/migrations) for production. Use DatabaseSync.plan rather than generic SchemaDiffer for SQLite rebuilds and MySQL catalogue-dependent alterations.

## Understand the direction

Pull asks “what exists in the database now?” Push asks “what must change to match this file?” Confusing them can replace your intended model with incomplete introspection or apply an old schema to a newer database. Keep the original schema in Git and start with pull output to a separate file or stdout.

Introspection cannot recover every application intention. Two SQL fields may look alike even though one was a schema enum and the other a String. Generator settings, aliases and `@updatedAt` need review too. Treat an introspected schema as input for comparison and refine it to the API you need.

## Plan before applying

Start with `--dry-run` on your development database and read the SQL. Look for drop/add operations, new NOT NULL columns and constraint changes. A technically valid plan may still fail on existing data: a new required field without a default needs a decision about old rows.

`--accept-data-loss` accepts warnings; it does not make the operation reversible. For a shared deployment history, store reviewed SQL as a [versioned migration](/next/en/migrations) planned against the previous state.

## Structure and data are separate checks

An empty structural plan says the supported structure matches the target. It does not prove business data correctness, application-level uniqueness or equal contents in two databases. Those need separate queries and checks.

After a successful push, a repeated plan should be empty. Otherwise check provider, URL, the SQLite working directory and supported definitions. For nontransactional DDL, inspect an unfinished journal first; another push does not automatically repair an interrupted one.
