It is easier to account for a limitation before it becomes an architectural assumption. Some query forms remain unsupported in 1.0.0. These cases need an explicit application decision.

## Queries and results

| Scenario | Current boundary | Application approach |
|---|---|---|
| Cursor with arbitrary `orderBy` | Combination is rejected | Use offset for that order or traverse the primary key |
| Top-N children for every included parent | `take` limits a related batch | Query children explicitly when a separate per-parent limit is required |
| Arbitrary projection shape | One generated projection class | Access selected fields and build an explicit DTO |
| Accessing an unloaded relation | Getter throws | Add include or omit the relation from the response |
| Concurrent upsert | Find/create-or-update, without atomic server upsert | Keep a unique constraint and handle conflicts |
| Scalar-array filtering and ordering | Deferred | Change the query model or use reviewed raw SQL |
| Typed full-text search | Not implemented | Index DDL does not imply a query API |

## Relation writes

Nested writes support small related operations, but they do not represent every change graph. Nested update beyond one relation level, deleting an owning-side required relation and writes with unknown ancestor keys are restricted.

For a complex operation, split supported writes into explicit steps inside a [transaction](/next/en/transactions). Key acquisition and write order then stay visible. Deleting or disconnecting a required relation must preserve the schema rule: a child cannot remain without its required parent.

## Names and schema

`count` conflicts with aggregates. Kotlin keywords are not escaped in every generated API form. Choose a safe client alias and retain the existing SQL name through `@map` when needed.

Multi-schema models, optimistic `@version` locking, read replicas and sharding are not implemented. Tenant isolation and soft delete need explicit application predicates. QueryInterceptor observes statements; it does not automatically add those rules.

## Providers and migrations

Introspection accepts representable structures and refuses definitions it cannot preserve correctly. Expression/partial indexes, triggers, generated columns, unsupported tables and other definitions can block pull or planning. Each provider has further [type and catalog limits](/next/en/databases).

H2/MySQL/MariaDB DDL implicitly commits. The journal records progress but does not make an entire file rollback-safe. A failure requires inspecting actual database state and [manual recovery](/next/en/migrations). PostgreSQL/SQLite have the documented transactional guarantees, which still require reviewing SQL and data before deployment.

## Async and compatibility

There is no R2DBC: JDBC occupies workers through futures and coroutines alike. Active statement cancellation in Volan 1.0 is a driver request, not a hard deadline or reversal of a completed commit. See [Async](/next/en/async).

Choose [compatible versions](/next/en/versions), regenerate on upgrades and verify against the target database. Release 1.0.0 does not imply support for every SQL shape or 100% test coverage. The runtime 85% coverage gate is deferred.
