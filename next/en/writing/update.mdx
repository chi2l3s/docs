An update has two independent parts: `where` selects rows and `data` supplies new values. First determine which record the user may change, then assign only fields that need replacement.

These fragments use an open `db` and the [User/Post schema](/next/en/schema). They first create a test user with a new email to make the operation self-contained. On a real database, use a validated application key rather than creating demonstration records.

## Change one user's name

<CodeGroup>
```kotlin Kotlin
val created = db.user.create { email = "edit@example.org"; name = "Before" }
val updated = db.user.update {
    where { id eq created.id }
    data { name = "After" }
}
println(updated.name)
```

```java Java
var created = db.getUser().create(data -> {
    data.setEmail("edit@example.org");
    data.setName("Before");
});
var updated = db.getUser().update(q -> {
    q.where(w -> w.getId().eq(created.getId()));
    q.data(data -> data.setName("After"));
});
System.out.println(updated.getName());
```
</CodeGroup>

The primary-key predicate matches at most one row. Only name changes; email remains unchanged. The method returns the updated `User`. A missing row raises `VolanNotFoundException`, unlike a bulk method's zero count.

## A broad filter is not limited to one row

<Warning>
On PostgreSQL and SQLite, `update` with a non-unique condition changes every matching row and returns one. Omitting `where` adds no protective condition. Use a full key for a specific record, or `updateMany` and inspect its count for a set of records.
</Warning>

H2 uses the row-returning path. The MySQL and MariaDB path without RETURNING checks selected rows and rejects multiple matches. This is dialect-specific behavior rather than a portable safety guard: always supply the correct key.

The method name is not a safety check. Include required tenant or owner conditions alongside the key in service code. Volan does not add those conditions automatically.

## An omitted field versus explicit null

```kotlin
val created = db.user.create { email = "clear@example.org"; name = "Alice" }
val cleared = db.user.update {
    where { id eq created.id }
    data { name = null }
}
println(cleared.name)
```

The name is cleared while email remains intact. Omitting the name assignment would leave it unchanged. Preserve this distinction for PATCH requests: a nullable value and a missing parameter must not collapse into the same action.

Runtime maintains `@updatedAt` during typed writes. Ordinary column defaults do not reapply on every update. Maintain handwritten SQL separately when it must follow the same timestamp rule.

## Update a set and inspect its count

```kotlin
val affected = db.user.updateMany {
    where { name.isNull() }
    data { name = "Unnamed" }
}
println("Updated rows: $affected")
```

Every user without a name receives `Unnamed`. The result is a `Long` affected-row count. With no missing names, it is `0L` rather than `VolanNotFoundException`.

Before a bulk operation, read or count the same predicate on a test database to understand scope. That does not freeze the set between commands under concurrent changes. Use a [transaction](/next/en/transactions) and suitable database isolation when checks and writes need one boundary.

## Avoid losing concurrent changes

A plain update replaces values. If two requests read one state and write their own versions, the later write can overwrite the earlier result. The DSL does not add automatic optimistic locking.

An application can define a version column, include its expected value in an `updateMany` predicate and increment it in the new payload. A zero count then needs application-specific handling as conflict or absence. This is an application protocol rather than an automatic built-in feature.
