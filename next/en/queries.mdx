Start with the model repository: `db.user` in Kotlin or `db.getUser()` in Java. A repository takes an operation description, builds SQL and returns records, projections or a row count. Ordinary operations do not require assembling column names as strings.

These examples use the [User/Post schema](/next/en/schema). `db` is an open client and the tables must already exist. The blocks show operations inside an application; [First query](/next/en/quickstart) covers the complete connection and table setup.

## CRUD

```kotlin
val created = db.user.create { email = "alice@example.org"; name = "Alice" }
val users = db.user.findMany {
    where { email endsWith "@example.org" }
    orderBy { id.asc() }
    take = 20
    skip = 0
}
db.user.update {
    where { id eq created.id }
    data { name = null }
}
val affected = db.user.updateMany {
    where { name.isNull() }
    data { name = "Unnamed" }
}
db.user.delete { where { id eq created.id } }
```

```java
var users = db.getUser().findMany(q -> {
    q.where(w -> w.getEmail().endsWith("@example.org"));
    q.orderBy(o -> o.getId().asc());
    q.setTake(20);
});
db.getUser().createMany(many -> {
    many.row(d -> d.setEmail("one@example.org"));
    many.row(d -> d.setEmail("two@example.org"));
});
```

`findMany` returns a list; `findFirst` and `findUnique` return nullable rows. Their `OrThrow` variants raise `VolanNotFoundException`. `create`, `update` and `delete` return the row; use a primary or unique key filter for `update` and `delete`. Their names do not guarantee that a broad filter changes only one row. `createMany`, `updateMany`, `deleteMany` return affected counts. Bulk inserts preserve defaults for omitted fields and keep all batches in one transaction.

`upsert { where { ... }; create { ... }; update { ... } }` uses find/create-or-update. It is not an atomic server upsert: concurrent creates can race and hit a unique constraint.

## Method results

Here, `User` is the generated entity and `UserProjection` holds selected columns. These are result types; their names follow your schema's model.

| Method | Kotlin result | When nothing matches |
| --- | --- | --- |
| `findMany` | `List<User>` | Empty list |
| `findFirst`, `findUnique` | `User?` | `null` |
| `findFirstOrThrow`, `findUniqueOrThrow` | `User` | `VolanNotFoundException` |
| `projectMany` | `List<UserProjection>` | Empty list |
| `projectFirst` | `UserProjection?` | `null` |
| `count` | `Long` | `0L` |
| `exists` | `Boolean` | `false` |
| `update`, `delete` | `User` | `VolanNotFoundException` |
| `updateMany`, `deleteMany` | `Long` | `0L` |

Java nullable results can also be `null`; the `Long` counts above become `long`. Check for a missing row before reading its properties.

`findUnique` uses the same first-row read path as `findFirst`. It does not verify that `where` names a unique key or report multiple matches. Uniqueness must follow from your predicate and database constraints: `id eq userId`, or equality on a complete unique key. `OrThrow` only changes missing-row behavior.

<Warning>
Use a specific row's key for `update` and `delete`. On PostgreSQL and SQLite, the SQL changes every row matching `where`, while the method returns one of them. Omitting `where` adds no protective predicate. Use `updateMany` or `deleteMany` for a set of rows and check the returned count.
</Warning>

MySQL and MariaDB additionally reject multiple matches for single-row writes. Do not rely on this as a portable check: use a unique key predicate for every provider.

`findMany` without `take` has no automatic page-size limit. Omitting `where` selects all rows; omitting `orderBy` provides no stable order. These defaults suit a small example, but your application must set page limits and access conditions.

## Filters

Scalar handles provide `eq`, `notEq`, `gt`, `gte`, `lt`, `lte`, `oneOf`, `notOneOf`; applicable string filters include `contains`, `startsWith`, `endsWith` and `ignoringCase()`. Nullable fields expose `isNull()` and `isNotNull()`. Group predicates with `and`, `or`, `not`. Java uses getters and method calls: `w.getId().eq(1)`, `w.or(o -> { ...; })`.

Values are bound parameters. For raw SQL, bind values in the parameters list; never concatenate user input into SQL. Dialects differ in case conversion; SQLite's built-in conversion is ASCII.

## Pagination

`take` limits and `skip` offsets. Use a deterministic order, including a unique tie-breaker. `cursor(id = lastId)` pages by primary key and excludes the cursor row unless `inclusive = true`. Supply every component of a composite key. Cursors with explicit `orderBy` are currently refused; use offset paging for that order.

## Summaries

`count()` and `exists()` do not load entities. `aggregate { count(); sum { views }; average { views } }` returns summaries. `groupBy { by { authorId }; count(); having { count gt 1L } }` returns grouped values. Reading fields not selected/grouped throws. [Projections and relations](/next/en/relations) explain partial results.

## Choose a read method

Use `findUnique` when you have a primary or unique key, such as a user's `id`. Use `findFirst` when several rows can match and your application wants the first one; set an order so that “first” has a defined meaning. `findMany` returns a list, including an empty list when no rows match.

A nullable result lets you handle a missing user as part of normal application behavior: return 404, offer registration or continue without the record. An `OrThrow` variant suits an internal operation that requires the row to exist. Avoid treating an expected missing record as an exceptional failure.

## Follow the CRUD example

The example creates Alice, reads users with the selected email suffix, orders by `id` and limits the page to twenty rows. The update clears only that user's name. `updateMany` then changes NULL names to `Unnamed` and returns the affected count. The delete addresses the created user by `id` again.

A write filter defines its scope. Before a bulk update or delete, check how many rows match and which authorization conditions are needed. Add tenant and soft-delete conditions to `where` explicitly; the runtime does not supply them for your application.

## Order and page size

`take` prevents an unbounded read but does not make its order stable. When ordering by a non-unique field, use a unique key to break ties. Otherwise, adjacent pages can overlap or miss rows.

Offset works well for straightforward numbered pages, but large `skip` values still make the database process skipped rows. Cursor pagination traverses the primary key; the current API cannot combine it with an arbitrary `orderBy`. Choose pagination around the order you need, as well as the UI.

## When you do not need entities

Use `exists` to check for a match and `count` to count rows. Select a projection when an HTTP response only needs emails. Aggregates calculate on the database side, so the application does not have to load every post to total its views. Relation filters likewise do not load the relation itself.

## Parameterized SQL

Use `rawQuery` for reads and `rawExecute` for changes when a repository cannot express an operation. These application fragments require an open `db` and the `User` table from [First query](/next/en/quickstart). If the email has no matching user, the result is an empty list.

```kotlin
val emailToFind = "alice@example.org"
val emails = db.rawQuery(
    """SELECT "email" FROM "User" WHERE "email" = ?""",
    listOf(emailToFind),
) { row -> row.getString("email") }
```

```java
var emailToFind = "alice@example.org";
var emails = db.rawQuery(
    "SELECT \"email\" FROM \"User\" WHERE \"email\" = ?",
    java.util.List.of(emailToFind),
    row -> row.getString("email")
);
```

Each `?` corresponds to one value in `parameters`, in order of appearance. Parameters bind values, not table names, column names or sort directions. Choose those SQL parts from a fixed application allowlist. The SQL above targets PostgreSQL and SQLite; the runtime does not translate arbitrary SQL between dialects.

The mapper runs for each row and constructs your result; raw queries have no automatic `include`. `getString` requires a non-null value; use `getStringOrNull` for a nullable column. `rawQuery` returns `List<T>` and adds no `LIMIT`: put the limit in your SQL.

`rawExecute(sql, parameters)` returns a `Long` affected-row count. For DDL, this value depends on the driver and does not count created tables. Both methods use the current connection inside `transaction`; separate calls outside it do not form one transaction. The generated client must be connected to a database: an executor-only client cannot run raw SQL.
