A query can wait for the network, a free connection or SQL execution. JDBC occupies a thread while it waits. In a server, run that work on workers with bounded concurrency so database waits do not consume every thread handling other events.

Java futures are available in alpha.2. Volan coroutine wrappers and active JDBC cancellation require alpha.3. Both APIs change how work is scheduled; JDBC itself remains blocking.

## Kotlin

Add `io.github.thirtyeighttwentysix:volan-coroutines` aligned with runtime via the alpha.3 BOM from the [staged repository](/next/en/build).

```kotlin
import io.github.thirtyeighttwentysix.volan.coroutines.CoroutineAccess
import io.github.thirtyeighttwentysix.volan.coroutines.suspendQuery
import kotlinx.coroutines.Dispatchers
import kotlinx.coroutines.withTimeout

val access = CoroutineAccess(Dispatchers.IO.limitedParallelism(4))
val users = withTimeout(2_000) {
    db.suspendQuery(access) { user.findMany { take = 20 } }
}
val created = db.suspendQuery(access) {
    transaction { tx ->
        tx.user.create { email = "async@example.org" }
    }
}
```

`suspendQuery` retains generated receiver and result types for clients and repositories. The shared default uses `Dispatchers.IO.limitedParallelism(16)`. A supplied dispatcher is application-owned. Size concurrency with the connection budget. Query and mapper callbacks execute on the worker; captured inputs must not be modified concurrently.

## Java

```java
var workers = java.util.concurrent.Executors.newFixedThreadPool(4);
try (var db = VolanClient.builder().url(url).asyncExecutor(workers).build()) {
    var result = db.getUser().findManyAsync(q -> q.setTake(20));
    var users = result.join();
} finally {
    workers.shutdown();
}
```

Repositories, transactions, rawQuery and rawExecute have `*Async` equivalents returning CompletableFuture. Default executor: ForkJoinPool.commonPool(). Use a dedicated executor for services. Volan does not shut it down. Finish work before closing the client. `join()` wraps failures in CompletionException; `get()` in ExecutionException. Empty nullable reads complete normally with null.

## Cancellation

Alpha.3 cancellation skips queued callbacks and requests `Statement.cancel()` for active JDBC work. Later statements are refused and an uncommitted transaction rolls back. Coroutine completion waits for worker, statement and connection cleanup. Future cancellation becomes visible immediately and does not wait for cleanup. Alpha.2 only skips queued Java work.

Cancellation is not a hard deadline. Drivers, pool checkout or commit may take time. It cannot undo committed writes or a commit already started. Configure connection, network and server timeouts separately. `mayInterruptIfRunning` does not control JDBC cancellation. JDBC remains blocking; this is not R2DBC.

## Workers and connections

Four workers do not imply four simultaneous queries when the pool has one connection. Other workers wait to acquire it. A larger pool likewise does not automatically increase CPU capacity or database server throughput.

Choose worker concurrency together with pool size and database load. Built-in SQLite uses one connection. For a server database, account for all application instances: each may own a pool. Observe waits and errors before increasing concurrency.

## Where to await the result

Java's `join()` blocks its calling thread until completion. That is useful in a small example or at a synchronous boundary, but calling `findManyAsync(...).join()` on an event loop brings blocking back to that sensitive thread. Continue from future completion using the framework's normal mechanism instead.

Kotlin's `suspendQuery` suspends the caller while a JDBC worker runs. Query callbacks and mapping run on that worker, so their inputs must be ready to cross the thread boundary. Do not mutate shared input while the query executes.

## A timeout does not prove rollback

The caller, pool, driver and database server have different waiting stages. A coroutine timeout describes how long the application will wait; it does not prove that a write was never persisted. Treat cancellation near commit carefully: before retrying, you may need to inspect state using a business key.

During shutdown, stop scheduling operations and wait for active work before closing the client and caller-owned executors. Shutting down an executor does not make unfinished callbacks successful queries.
