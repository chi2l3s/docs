Если создание пользователя и его первой публикации — одна операция приложения, они должны завершиться вместе. Без транзакции пользователь может сохраниться, а публикация — упасть с ошибкой. `transaction` удерживает связанные операции на одном соединении и позволяет откатить незавершённые изменения.

В примере callback создаёт автора, использует его `id` при записи публикации и возвращает пользователя. Внутри callback работай через переданный `tx`: это клиент текущей транзакции.

```kotlin
val created = db.transaction { tx ->
    val user = tx.user.create { email = "transaction@example.org" }
    tx.post.create { title = "Welcome"; authorId = user.id }
    user
}
```

Java использует `db.transaction(tx -> { ...; return result; })` либо `transactionAsync(...).join()` вне другой транзакции.

Весь callback работает на одном потоке и соединении. Нормальное завершение делает commit, исключение — rollback. Вложенная синхронная транзакция создаёт savepoint. Откат DDL — отдельная [гарантия СУБД](/next/ru/databases), он не следует из транзакционности DML.

## Изоляция и повторы

`Isolation.DEFAULT` использует настройки драйвера. Явные уровни зависят от СУБД; SQLite поддерживает SERIALIZABLE и READ_UNCOMMITTED. По умолчанию используй `RetryPolicy.NONE`. Настроенный retry повторяет весь внешний callback при повторяемой ошибке транзакции: код должен допускать повторное выполнение. Платежи, HTTP, отправку сообщений и другие необратимые эффекты выполняй снаружи.

Из подключённой транзакции нельзя отправлять async или coroutine работу на другой поток. Используй синхронные операции `tx`. Не возвращай future из callback и не запускай в нём дочерние корутины.

Для корутин отправляй целую `transaction` через [suspendQuery](/next/ru/async). Callback остаётся синхронным. Клиенты поверх bare QueryExecutor не владеют соединением и не предоставляют guards подключённой транзакции.

## Параметры transaction

`transaction(isolation, retry, block)` возвращает результат callback после успешного commit. Если commit завершается ошибкой, этот результат не возвращается. В Kotlin параметры можно назвать; в Java передай `Isolation`, `RetryPolicy` и callback в таком порядке. Без явных параметров используются `Isolation.DEFAULT` и `RetryPolicy.NONE`.

| Параметр RetryPolicy | Значение | Смысл |
| --- | --- | --- |
| `attempts` | Обязательное, минимум `1` | Общее число запусков, включая первый |
| `initialDelay` | `20L` | Задержка перед вторым запуском, миллисекунды |
| `multiplier` | `2.0` | Множитель задержки перед последующими запусками |
| `RetryPolicy.NONE` | `attempts = 1` | Одна попытка без повторов |
| `RetryPolicy.DEFAULT` | `attempts = 3` | До трёх попыток; ожидания по умолчанию 20 и 40 мс |

Имя `RetryPolicy.DEFAULT` не означает, что эта политика включена автоматически. Runtime повторяет только внешний callback после `VolanTransactionException` с `retryable = true`, пока не исчерпаны `attempts`. Unique constraint, неверное поле и произвольное исключение приложения не запускают такой повтор.

Вложенный `transaction` создаёт savepoint и использует изоляцию внешней транзакции. Переданные вложенному вызову `isolation` и `retry` не открывают независимую транзакцию и не запускают отдельный цикл повторов. Если повторяемая ошибка выйдет до внешней границы, повторится весь внешний callback при включённой политике.

## Настроить ограниченный повтор

Фрагмент использует уже открытый `db` и таблицу `User` из [Первого запроса](/next/ru/quickstart). Он создаёт пользователя с заданным email. Перед запуском убедись, что этот email ещё не занят. Повтор разрешён для временной ошибки транзакции; повторный отдельный запуск примера с тем же email завершится конфликтом уникальности.

```kotlin
import io.github.thirtyeighttwentysix.volan.runtime.Isolation
import io.github.thirtyeighttwentysix.volan.runtime.RetryPolicy

val emailToCreate = "transaction@example.org"
val created = db.transaction(
    isolation = Isolation.DEFAULT,
    retry = RetryPolicy(attempts = 3, initialDelay = 20L, multiplier = 2.0),
) { tx ->
    tx.user.create { email = emailToCreate }
}
```

После успешного завершения `created.email` равен `emailToCreate`, а запись сохранена. Email подготовлен до callback, поэтому каждая попытка использует один вход. Отправку приветственного письма выполняй после возвращения `transaction`, когда commit уже завершён.

## Время жизни клиента

Держи транзакции короткими. Закрывай клиент при остановке приложения после завершения работы. Переданный DataSource остаётся собственностью приложения. Не считай, что Spring `@Transactional` автоматически присоединяет транзакцию Volan.

## Когда изменения становятся видимыми

Нормальный возврат из callback означает, что Volan может выполнить commit. Если исключение выходит наружу, runtime выполняет rollback. Не перехватывай внутри callback ошибку, после которой вся операция должна считаться неуспешной: если проглотить её и вернуть результат, внешняя транзакция может завершиться нормально.

Savepoint вложенной синхронной транзакции позволяет откатить её часть. Он не создаёт независимый commit: изменения вложенного callback всё ещё зависят от результата внешней транзакции. Внешний rollback откатит и успешно завершённую вложенную часть.

## Что нельзя включать в retry

Повтор транзакции заново выполняет callback целиком. Если callback отправил письмо, следующий запуск может отправить его ещё раз, даже если предыдущие SQL-изменения откатились. Поэтому сохраняй необходимые данные в транзакции, а внешние эффекты запускай после успешного результата; для строгой согласованности нужен отдельный механизм приложения, например обработка сохранённого события.

Похожая проблема возникает с меняющимися захваченными данными. Перед callback подготовь неизменяемые входные значения. Retry не решает конфликт любой природы: повторять имеет смысл только ошибки, для которых операция допускает новый запуск.

## Почему callback должен оставаться синхронным

Подключённая транзакция привязана к потоку и соединению. Если вынести один из её запросов в future или дочернюю корутину, появится работа вне ожидаемого контекста. Отправляй на JDBC worker всю транзакцию целиком, а внутри используй обычные операции `tx`.

Транзакция также удерживает ресурсы базы. Долгий HTTP-запрос внутри callback увеличивает время удержания соединения и блокировок. Проверь входные данные до открытия транзакции и оставь внутри только необходимые обращения к БД.
