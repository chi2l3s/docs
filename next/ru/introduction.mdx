Пользователь, его публикации, несколько фильтров и одна транзакция — с этого часто начинается работа с базой. Volan позволяет описать эти данные в `schema.volan` и получить клиент, в котором имена моделей, полей и связей уже известны компилятору.

В Kotlin запрос читается как небольшой блок с условиями. В Java та же операция доступна через методы и callbacks. Под ними работает JDBC: клиент строит SQL, передаёт значения параметрами и превращает результат в сгенерированные объекты.

## От схемы к запросу

Допустим, в приложении есть модель `User` с `id`, `email` и `name`. После генерации у клиента появляется репозиторий `db.user`. Чтобы получить пользователя, ты обращаешься к полю `id` в типизированном условии:

```kotlin
val user = db.user.findUnique {
    where { id eq userId }
}
```

Здесь `db` — подключённый клиент, а `userId` — идентификатор из приложения. Результат может быть `null`: отсутствие строки является обычным результатом чтения. Для ситуации, где строка обязана существовать, есть вариант `findUniqueOrThrow`.

Клиент знает имена полей из схемы. Если изменить модель и заново сгенерировать код, места использования удалённого поля перестанут компилироваться. Это помогает увидеть несогласованность в коде ещё до запроса к базе. Состояние самой базы проверяется отдельно: успешная компиляция не означает, что нужная таблица уже создана.

## Три части приложения

| Часть | Что хранит и делает | Когда меняется |
|---|---|---|
| `schema.volan` | Модели, типы, ключи, связи и настройки генератора | Когда меняется модель данных |
| Сгенерированный клиент | Репозитории, формы записи, фильтры и маппинг результата | При генерации из схемы |
| База данных | Таблицы, ограничения, индексы и сами строки | При миграциях и запросах приложения |

Эти части должны соответствовать друг другу. Добавление поля в схему сначала меняет описание, генерация обновляет API, а миграция меняет таблицу. Каждый шаг выполняется явно. Поэтому сборку можно запускать без credentials и без подключения к production-базе.

## Что стоит знать заранее

Связи загружаются явно через `include`: чтение свойства не запускает скрытый SQL-запрос. Транзакции задаются callback клиента. Для HTTP-ответов ты выбираешь поля и собираешь DTO. Это делает обращение к базе заметным в коде и позволяет разбирать количество запросов по конкретным операциям.

JDBC остаётся блокирующим даже при использовании futures или корутин. Tenant isolation и soft delete также требуют условий приложения: они не добавляются автоматически. Перед выбором для проекта прочитай [Ограничения](/next/ru/limitations) и особенности своей [СУБД](/next/ru/databases).

## Что появится после генерации

Из модели получается целый путь работы с данными. Сущность представляет прочитанную строку. Репозиторий выбирает операцию. Where-форма предлагает только поля модели и совместимые сравнения. Create- и update-формы принимают значения записи, а сгенерированный mapper читает JDBC-строку в известные типы.

Например, у публикации `views Int` есть числовые сравнения, а у заголовка — поиск по подстроке. После переименования поля и генерации компилятор покажет прежние обращения в коде. Это особенно полезно, когда один набор моделей используют Kotlin- и Java-части приложения.

Ты по-прежнему решаешь, какие строки доступны пользователю и сколько данных запросить. Клиент помогает выразить запрос, а правила доступа, DTO и эксплуатация базы остаются явными частями приложения.
