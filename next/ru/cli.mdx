CLI полезен, когда работа со схемой должна быть отдельной проверяемой операцией: перед commit, в CI или при подключении существующей базы. Он читает `schema.volan`, показывает диагностику и выполняет только указанную команду.

Для запуска нужна Java 17+. Сначала [установи CLI](/next/ru/installation), затем проверь [версию генератора](/next/ru/versions). Текущий preview рассчитан на API alpha.3; его нельзя подставлять в сборку с runtime alpha.2.

```bash
volan --help
volan init --provider sqlite --package example.generated --java-friendly
volan validate --schema schema.volan
volan format --schema schema.volan --check
volan generate --schema schema.volan --output build/generated/volan
volan db push --schema schema.volan --url jdbc:sqlite:./data.db --dry-run
volan db pull --url jdbc:sqlite:./data.db --stdout
```

| Команда | Параметры | Результат |
|---|---|---|
| init | --schema, --provider, --package, --java-friendly | Создать схему без перезаписи |
| validate | --schema | Диагностика синтаксиса и семантики |
| format | --schema, --check, --stdout | Форматировать, сравнить или напечатать |
| generate | --schema, --output | Kotlin и manifest собственных файлов |
| db pull | --schema, --url, --stdout, --force | Прочитать структуру БД |
| db push | --schema, --url, --dry-run, --accept-data-loss, --resolve | План, применение или проверка восстановления |

По умолчанию: `schema.volan`, provider init `postgresql`, package `com.example.volan`, Java callbacks выключены без `--java-friendly`.

Format проверяет синтаксис; validate — также семантику. `--check` и `--stdout` несовместимы. Format check завершается с ненулевым кодом при отличиях, не меняя файл. Генерация разрешает output относительно текущего проекта, проверяет схему и не открывает БД.

URL должен использовать JDBC; provider и URL должны соответствовать. DATABASE_USER и DATABASE_PASSWORD задают credentials серверной БД. Не записывай реальные секреты в схему или команды. `--resolve` и `--dry-run` несовместимы.

Перед применением прочитай [Синхронизацию](/next/ru/sync) и [Миграции](/next/ru/migrations). Команд migrate, studio, self-update и native-image CLI нет. Init не создаёт Gradle/Maven-проект.

## Обычный цикл работы со схемой

После изменения модели запусти `validate`: правильно отформатированный файл может всё ещё содержать неверную связь или ключ. Затем выполни `format --check`, если нужно убедиться, что файл соответствует общему стилю. Перед commit можно запускать обе команды; они не требуют подключения к БД.

Генерация обновляет API клиента, а компиляция проверяет места использования этого API. Если генерация уже привязана к сборке, отдельный ручной `generate` обычно не нужен. Изменение таблиц выполняется другим шагом: сначала plan/dry-run, затем проверенное применение.

## Команды в CI

`format --check` не меняет файл и возвращает ненулевой код при отличиях, поэтому подходит для проверки. `--stdout` нужен, когда результат форматирования или pull требуется просмотреть либо сохранить самостоятельно. Не смешивай его с `--check`.

Для генерации фиксируй CLI или codegen version вместе с runtime. Так обновление системного executable не изменит API неожиданно для сборки. Проверка схемы и компиляция могут идти без credentials; доступ к БД нужен только командам, которые действительно читают или меняют её.

## Явный путь и явная база

Команды разрешают пути относительно текущего каталога. Если запускаешь CLI из другой папки, передай `--schema` явно и проверь output. Для SQLite также учитывай относительный файл в JDBC URL. Особенно перед push убедись, что команда смотрит на нужную development-базу.

Подробности SQL-плана и восстановления не скрыты за командой generate: они описаны отдельно в [Синхронизации](/next/ru/sync) и [Миграциях](/next/ru/migrations).
