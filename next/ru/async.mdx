Запрос к БД может ждать сеть, свободное соединение или выполнение SQL. JDBC в это время занимает поток. В сервере такой запрос стоит выполнять на workers с ограниченным параллелизмом, чтобы ожидание БД не заняло все потоки обработки других событий.

Java futures доступны в alpha.2. Модуль корутин Volan и отмена активного JDBC относятся к Volan 1.0. Оба подхода меняют организацию выполнения; сама работа JDBC остаётся блокирующей.

## Kotlin

Добавь `io.github.thirtyeighttwentysix:volan-coroutines`, согласованный с runtime через BOM 1.0.0 из Maven Central; см. [Сборку](/next/ru/build).

```kotlin
import io.github.thirtyeighttwentysix.volan.coroutines.CoroutineAccess
import io.github.thirtyeighttwentysix.volan.coroutines.suspendQuery
import kotlinx.coroutines.Dispatchers
import kotlinx.coroutines.withTimeout

val access = CoroutineAccess(Dispatchers.IO.limitedParallelism(4))
val users = withTimeout(2_000) {
    db.suspendQuery(access) { user.findMany { take = 20 } }
}
val created = db.suspendQuery(access) {
    transaction { tx ->
        tx.user.create { email = "async@example.org" }
    }
}
```

`suspendQuery` сохраняет типы сгенерированного receiver и результата клиента или репозитория. По умолчанию используется общий `Dispatchers.IO.limitedParallelism(16)`. Переданный dispatcher принадлежит приложению. Согласуй параллелизм с бюджетом соединений. Query и mapper callbacks работают на worker; не меняй захваченные входные данные параллельно.

## Java

```java
var workers = java.util.concurrent.Executors.newFixedThreadPool(4);
try (var db = VolanClient.builder().url(url).asyncExecutor(workers).build()) {
    var result = db.getUser().findManyAsync(q -> q.setTake(20));
    var users = result.join();
} finally {
    workers.shutdown();
}
```

Репозитории, transaction, rawQuery и rawExecute имеют варианты `*Async`, возвращающие CompletableFuture. По умолчанию используется ForkJoinPool.commonPool(). Для сервиса выдели отдельный executor. Volan не закрывает его. Заверши работу до закрытия клиента. `join()` оборачивает ошибки в CompletionException, `get()` — в ExecutionException. Пустое nullable-чтение нормально завершается с null.

## Отмена

Volan 1.0 пропускает отменённые queued callbacks и вызывает `Statement.cancel()` для активного JDBC. Следующие statements запрещены, незавершённая транзакция откатывается. Корутина завершается после освобождения worker, statement и соединения. Future становится cancelled сразу, без ожидания cleanup. Alpha.2 лишь пропускает queued Java-операции.

Отмена не гарантирует жёсткий дедлайн. Драйвер, получение соединения и commit могут занять время. Она не отменяет завершённую запись или уже начавшийся commit. Настрой таймауты пула, сети и сервера отдельно. `mayInterruptIfRunning` не управляет отменой JDBC. JDBC остаётся блокирующим; это не R2DBC.

## Параллелизм и соединения

Четыре workers не означают четыре одновременно выполняющихся запроса, если пул БД содержит одно соединение. Оставшиеся workers будут ждать его получения. И наоборот, большой пул сам по себе не даёт приложению больше CPU или пропускной способности сервера базы.

Выбирай бюджет workers вместе с размером пула и нагрузкой на БД. Для встроенной SQLite используется одно соединение. У серверной БД учитывай количество экземпляров приложения: каждый экземпляр может держать собственный пул. Наблюдай время ожидания и ошибки, прежде чем увеличивать параллелизм.

## Где ждать результат

В Java `join()` блокирует вызывающий поток до результата. Это удобно для небольшого примера или синхронной границы, но вызов `findManyAsync(...).join()` прямо на event loop вернёт блокировку в тот же чувствительный участок. В таком приложении продолжай обработку после завершения future средствами фреймворка.

В Kotlin `suspendQuery` освобождает вызывающую корутину на время JDBC worker. Блок описания запроса и маппинг выполняются на worker, поэтому передаваемые значения должны быть готовы к этому переносу. Не меняй общий mutable input во время выполнения.

## Таймаут не равен откату

У клиента, пула, драйвера и сервера разные этапы ожидания. Таймаут корутины выражает, сколько приложение готово ждать, но не доказывает, что запись не успела сохраниться. Особенно осторожно обрабатывай результат, если отмена произошла около commit: перед повтором операции может потребоваться проверка состояния по бизнес-ключу.

Во время остановки сервиса сначала прекрати создавать новые операции и дождись активных. После этого закрывай клиент и собственные executors. `shutdown()` executor не превращает незавершённые callbacks в успешно выполненные запросы.
