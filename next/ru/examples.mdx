Пример полезен, когда понятно, какую часть он проверяет. Первый запуск показывает полный путь от схемы до строки в SQLite. Примеры интеграции показывают lifecycle клиента и перенос JDBC. Независимые примеры приложений проверяют, что опубликованные или подготовленные artifacts можно использовать вне исходного проекта Volan.

Начни с [Первого запроса](/next/ru/quickstart), если знакомишься с ORM. Для существующего приложения выбери раздел [Фреймворки](/next/ru/frameworks). Проверки плагинов сборки ниже нужны, когда пробуешь alpha.3 из исходников.

Схема H2 plugin consumer:

```prisma
datasource db {
  provider = "h2"
  url = env("UNSET_PLUGIN_SMOKE_URL")
}
generator client {
  provider = "volan-kotlin"
  package = "example.generated"
  javaFriendly = true
}
model User {
  id Int @id @default(autoincrement())
  name String
}
```

Тесты Kotlin/Java явно создают User до записи и закрывают клиент. [Сборка](/next/ru/build) содержит полную конфигурацию Gradle/Maven.

После подготовки alpha.3 из корня репозитория:

```bash
python scripts/verify-plugins.py --version 0.1.0-alpha.3 --repository build/release-repository
./gradlew -p release-smoke test "-PvolanVersion=0.1.0-alpha.2" --tests smoke.PublishedSqliteTest
```

Verifier копирует consumers перед изменением схем, проверяет обычную сборку, configuration cache, удаление source/bytecode модели и восстановление из Gradle build cache. Если Maven отсутствует в PATH, передай `--maven /path/to/mvn`. SQLite release test не требует Docker; отдельный тест не означает проверку всей серверной suite.

## Что проверить в своём проекте

Сначала воспроизведи маленький сценарий без изменений: генерация, компиляция, создание таблицы, запись и чтение. Затем меняй по одной части — provider, модель или integration lifecycle. Когда всё меняется одновременно, причина ошибки становится менее очевидной.

API-примеры используют одну схему User/Post. Чтобы выполнить их после quickstart, добавь модель Post, обнови сгенерированный клиент и примени соответствующий DDL. Одной генерации недостаточно, потому что она не меняет SQLite-таблицы.

## Что проверяет внешнее приложение

Пример приложения собирается из внешних artifacts и показывает, что кодогенерация и runtime действительно работают вместе. Он также обнаруживает ошибки публикации, которые тесты внутренних модулей могут не увидеть: отсутствующий dependency, неверные plugin markers или незарегистрированные generated sources.

H2 consumer не является доказательством всех гарантий PostgreSQL/MySQL. Для целевого provider запускай соответствующие проверки и проверяй миграции на предыдущей структуре с данными. Полный web lifecycle тоже проверяется отдельно от маленького CRUD-сценария.

## Запустить примеры подробных руководств

[Проект User/Post](https://github.com/chi2l3s/docs/tree/main/examples/query-guide-next) содержит схему, создание тестовых таблиц и Kotlin/Java-примеры [чтения](/next/ru/querying/reading), [фильтров](/next/ru/querying/filtering), [пагинации](/next/ru/querying/ordering-pagination), [агрегатов](/next/ru/querying/aggregation) и [записи](/next/ru/writing/create).

В каталоге проекта запусти:

```bash
./gradlew test "-PvolanRepository=file:///ABSOLUTE/PATH/TO/release-repository"
```

Для PowerShell используй `.\gradlew.bat` вместо `./gradlew`. Нужен JDK 25. Каждая проверка создаёт свою SQLite-базу в памяти, выполняет операцию и проверяет результат. Временные данные исчезают при закрытии клиента. Схемы из раздела схемы также генерируются и компилируются в отдельных packages.

Подготовь библиотеки по [руководству сборки](/next/ru/build) и замени `ABSOLUTE/PATH/TO/release-repository` абсолютным путём своего файлового Maven-репозитория. Эти артефакты alpha.3 не опубликованы в Central.
