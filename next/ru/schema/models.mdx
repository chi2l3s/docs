Модель описывает записи одного вида: пользователей, публикации, заказы. Из блока `model` Volan создаёт сущность, репозиторий, условия запросов и формы записи. В базе этой модели соответствует таблица. Само объявление не создаёт таблицу: изменение структуры нужно применить отдельно через [синхронизацию](/next/ru/sync) или [миграцию](/next/ru/migrations).

## Начни с одной записи

Этот блок можно добавить в `schema.volan` с уже настроенными `datasource` и `generator`:

```prisma
model User {
  id Int @id @default(autoincrement())
  email String @unique
  name String?
}
```

У пользователя есть идентификатор, обязательный email и необязательное имя. База выдаёт `id` при вставке, если приложение его не передало. `@unique` на email означает ограничение базы: две строки с одним и тем же email должны конфликтовать. Регистр и правила сравнения зависят от СУБД и настройки колонки.

После генерации появляется `db.user` в Kotlin и `db.getUser()` в Java. Имя модели остаётся `User`. Генератор не создаёт отдельный метод `findByEmail`: поиск выражается через `findUnique { where { email eq ... } }`. Его поведение разобрано в [чтении записей](/next/ru/querying/reading).

## Первичный и уникальный ключ — разные решения

Первичный ключ идентифицирует строку для операций клиента и курсорной пагинации. У модели должен быть один такой ключ: поле с `@id` или набор полей в `@@id`. Его части обязательны и не могут быть списками.

Если идентификатор состоит из нескольких значений, опиши их вместе. Здесь членство определяется парой «организация, пользователь»:

```prisma
model Membership {
  organizationId Int
  userId Int
  role String

  @@id([organizationId, userId])
}
```

Две строки с одинаковой парой недопустимы, но один пользователь может состоять в разных организациях. Поиск конкретного членства должен передать обе части. Если выбрать только `userId`, условию могут соответствовать несколько строк.

`@@unique([organizationId, userId])` решает задачу дополнительной уникальности, если у модели уже есть другой первичный ключ. Уникальное ограничение не заменяет требование первичного ключа у обычной модели. Оно также не добавляет проверки прав доступа: организация в фильтре остаётся ответственностью приложения.

## Имена в коде и в SQL

Без mapping таблица называется точно как модель, а колонка — точно как поле. Автоматического превращения `User` в `users` или `createdAt` в `created_at` нет.

```prisma
model Account {
  id Int @id @default(autoincrement())
  emailAddress String @unique @map("email_address")

  @@map("accounts")
}
```

В клиенте ты обращаешься к `Account.emailAddress`, а SQL использует таблицу `accounts` и колонку `email_address`. Это удобно для существующей базы. При переименовании проверь SQL миграции: новый mapping сам по себе не доказывает, что план сохранит данные через `RENAME`.

## Когда нужен индекс

Индекс помогает базе находить и упорядочивать строки по выбранным колонкам. Он не меняет тип результата запроса и не делает строки уникальными.

```prisma
model Article {
  id Int @id @default(autoincrement())
  authorId Int
  publishedAt DateTime

  @@index([authorId, publishedAt])
}
```

Такой индекс стоит рассмотреть для списка публикаций одного автора по времени. Его полезность проверяют на реальном плане запроса своей СУБД. Добавление индекса в схему требует обновления таблиц; повторная генерация клиента этого не делает.

## Таблица без подходящего ключа

Для чужой таблицы, которой клиент не должен управлять, есть `@@ignore`. Игнорируемая модель может не иметь первичного ключа, и репозиторий для неё не генерируется. Это не механизм разграничения доступа. Если приложение не должно видеть определённые данные, права базы и DTO задаются отдельно.
