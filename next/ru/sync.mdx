При подключении существующей базы удобно начать с её структуры. `pull` читает каталоги БД и создаёт представимое описание в формате Volan. Когда схема уже написана, `push` строит план перехода от фактической структуры к желаемой и может применить его к development-базе.

Обе операции работают с таблицами и ограничениями. Генерация клиента — отдельный этап: она читает файл схемы, не соединяется с БД и не запускает push автоматически.

## CLI

```bash
volan db push --schema schema.volan --url jdbc:sqlite:./data.db --dry-run
volan db push --schema schema.volan --url jdbc:sqlite:./data.db
volan db pull --url jdbc:sqlite:./data.db --stdout
```

CLI preview поддерживает эти команды отдельно от генерации runtime. DATABASE_URL должен быть JDBC URL. Push читает URL datasource, если он не переопределён `--url`; pull использует DATABASE_URL или `--url`. Для серверной БД задай DATABASE_USER и DATABASE_PASSWORD через окружение или secret manager.

Pull печатает схему с `--stdout` либо создаёт `--schema introspected.volan`. Замена файла требует `--force`. Экспорт использует env("DATABASE_URL"), не credentials. Сохраняй исходную схему: pull не восстановит все объявления клиента.

## Библиотека

Для SQLite alpha.2 добавь `volan-migrate` в зависимости [первого запроса](/next/ru/quickstart), выравнивая версию через BOM.

```kotlin
import io.github.thirtyeighttwentysix.volan.ir.SchemaLoader
import io.github.thirtyeighttwentysix.volan.dialect.sqlite.SqliteDialect
import io.github.thirtyeighttwentysix.volan.migrate.DatabaseSync
import io.github.thirtyeighttwentysix.volan.migrate.SqliteReader
import java.nio.file.Files
import java.nio.file.Path
import java.sql.DriverManager

val schema = SchemaLoader.load("schema.volan",
    Files.readString(Path.of("schema.volan"))).schemaOrThrow()
val sync = DatabaseSync(SqliteReader(), SqliteDialect)
DriverManager.getConnection("jdbc:sqlite:./data.db").use { connection ->
    val plan = sync.plan(connection, schema)
    println(plan.toSql(SqliteDialect))
    sync.push(connection, schema)
}
```

Используй отдельные JDBC-соединения, начинающие в auto-commit. Перед применением отобрази и проверь план; не принимай разрушительные изменения автоматически из недоверенного ввода. `sync.plan` — actual → desired, `sync.drift(connection, SchemaMapper.map(expectedSchema))` — expected → actual. Сравнивается структура, а не данные; операции лишь читают каталоги.

## История изменений

Предупреждения требуют явного `--accept-data-loss`. Warning может означать ошибку на существующих строках, а не только потерю данных. Rename представляется как drop/add; для сохранения данных используй проверенный ALTER RENAME SQL.

PostgreSQL/SQLite push проверяет структуру до commit транзакции. H2/MySQL/MariaDB могут оставить committed DDL и используют отдельный журнал `_volan_push` с [ручным восстановлением](/next/ru/migrations). Успешный повторный push пуст.

Push не создаёт migration files и не добавляет versioned history. Для production применяй [версионируемые миграции](/next/ru/migrations). Для SQLite rebuild и MySQL catalogue-dependent alterations используй DatabaseSync.plan вместо общего SchemaDiffer.

## Разбери направление операции

Pull отвечает «что сейчас существует в базе?». Push отвечает «что нужно изменить, чтобы база соответствовала файлу?». Если перепутать направление, можно заменить своё описание неполной интроспекцией или применить старую схему к более новой базе. Сохраняй исходную схему в Git и выполняй pull сначала в отдельный файл либо stdout.

Introspection не восстанавливает все намерения разработчика. Два SQL-поля могут выглядеть одинаково, хотя одно было enum в схеме, а другое — String. Generator settings, aliases и `@updatedAt` тоже требуют проверки. Прочитанная схема — материал для сравнения, который нужно довести до нужного API.

## План сначала, применение потом

На своей development-базе начни с `--dry-run` и прочитай SQL. Обрати внимание на drop/add, новые NOT NULL колонки и изменения ограничений. Даже технически корректный план может быть неприемлемым для текущих данных: добавление обязательного поля без default требует решения, чем заполнить старые строки.

`--accept-data-loss` означает согласие на предупреждения, но не делает операцию обратимой. Если нужна переносимая история изменений для команды и deployment, сохрани проверенный SQL как [версионируемую миграцию](/next/ru/migrations), построенную относительно предыдущего состояния.

## Структура и данные — разные проверки

Пустой structural plan говорит, что поддерживаемая структура соответствует цели. Он не доказывает корректность бизнес-данных, отсутствие дублей в логике приложения или одинаковое содержимое двух баз. Для этого нужны отдельные запросы и проверки.

После применения push повторный план должен быть пустым. Если это не так, проверь provider, URL, рабочий каталог для SQLite и поддерживаемые определения. Для nontransactional DDL сначала разберись с незавершённым журналом; новый push не является автоматическим восстановлением предыдущего.
