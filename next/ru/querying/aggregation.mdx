Для статистики не обязательно загружать все публикации в память. База может сама посчитать их количество, сумму просмотров и среднее. `aggregate` возвращает один результат по выборке, а `groupBy` — список результатов по группам, например по каждому автору.

Фрагменты используют открытый `db`, таблицы и [схему User/Post](/next/ru/schema), где `Post.views` — целое число. Агрегаты не возвращают публикации и не загружают связи.

## Один результат по выбранным строкам

```kotlin
val stats = db.post.aggregate {
    where { views gt 0 }
    count()
    sum { views }
    average { views }
    minimum { views }
    maximum { views }
}
println("Posts: ${stats.count}")
println("Views: ${stats.sumOfViews}")
println("Average: ${stats.averageOfViews}")
```

Условие сначала исключает публикации без просмотров. Каждая функция запрашивается явно, и результат содержит ответы на эти вопросы. `count()` считает строки, а не сумму просмотров.

| Запрос | Свойство | Тип Kotlin |
| --- | --- | --- |
| `count()` | `count` | `Long` |
| `sum { views }` | `sumOfViews` | `BigDecimal?` |
| `average { views }` | `averageOfViews` | `Double?` |
| `minimum { views }` | `minimumOfViews` | `Int?` |
| `maximum { views }` | `maximumOfViews` | `Int?` |

Числовая сумма возвращается как `BigDecimal?`, среднее — `Double?`; минимум и максимум сохраняют тип скалярного поля с nullable-результатом. Числовые функции доступны на числовых полях, экстремумы — на поддерживаемых упорядоченных полях.

## Пустая выборка и незапрошенный агрегат

Когда совпадений нет, запрошенный count равен нулю. Сумма, среднее, минимум и максимум могут быть null: математический результат для отсутствующих данных отличается от нуля просмотров.

Если вызван только `count()`, чтение `sumOfViews` вызывает `VolanAggregateNotAskedException`. Свойство в сгенерированном классе существует, но запрос его не вычислял. Запрашивай всё, что планируешь читать. Если интерфейс должен показывать ноль вместо отсутствия суммы, делай такую подстановку осознанно на уровне приложения.

## По одному результату на автора

```kotlin
val groups = db.post.groupBy {
    where { views gt 0 }
    by { authorId }
    count()
    sum { views }
    having { count gt 1L }
    orderBy {
        authorId.asc()
    }
    take = 10
}
groups.forEach { group ->
    println("${group.authorId}: ${group.count} posts, ${group.sumOfViews} views")
}
```

`where` отбирает исходные публикации. `by { authorId }` собирает их по автору. `having` оставляет только группы с более чем одной подходящей публикацией. Затем группы сортируются по `authorId`. В результате не более десяти групп.

В этой версии сгенерированный groupBy `orderBy` предлагает поля модели, а не свойства агрегатов вроде `sumOfViews`. Для корректного SQL сортируй по ключам из `by`. Если нужен именно топ по сумме, вырази сортировку агрегата в собственном SQL; сортировка по агрегатам через этот DSL пока не поддерживается.

Именно порядок этих смысловых шагов отличает where от having. `views gt 0` — условие конкретной строки, а `count gt 1L` — условие уже вычисленной группы. Перенести одно в другое без изменения результата нельзя.

## Поля группировки и частичный результат

Можно перечислить несколько полей в `by`, чтобы получить группы по их сочетанию. Читать разрешается ключи, включённые в `by`, и заказанные агрегаты. Обычная колонка, например `title`, не становится однозначной для группы из нескольких публикаций; её чтение как незапрошенного поля вызывает ошибку.

Если подходящих групп нет, результат — пустой список. Не обращайся к `groups[0]` без проверки. Для сводной статистики по всем строкам вместо искусственной одной группы используй `aggregate`.

В Java доступны те же callbacks: `q.by(b -> b.authorId())`, `q.sum(s -> s.views())`, `q.having(h -> h.getCount().gt(1L))`. Поля результата читаются через getters, например `getSumOfViews()`.

Для оконных функций или специфичной аналитики, которую этот API не выражает, переходи к [raw SQL](/next/ru/querying/raw-sql), задавая mapping и параметры явно.
