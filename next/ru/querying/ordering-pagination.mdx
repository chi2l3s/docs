Страница результатов — это выбранные строки, определённый порядок и ограниченный размер. Без порядка две последовательные выборки могут вернуть записи по-разному. Без лимита небольшой пример легко превращается в чтение всей таблицы.

Фрагменты используют открытый `db` и [модели User/Post](/next/ru/schema). Значения страницы и курсора обычно приходят из приложения; ниже они задаются прямо в примере.

## Порядок с разрешением совпадений

```kotlin
val posts = db.post.findMany {
    orderBy {
        views.desc()
        id.asc()
    }
    take = 20
}
```

Сначала идут публикации с большим числом просмотров. Когда просмотры одинаковы, порядок определяет уникальный `id`. Второе поле делает порядок однозначным. Поля применяются в порядке объявления.

Кроме `asc()` и `desc()` есть `ascNullsFirst()`, `ascNullsLast()`, `descNullsFirst()`, `descNullsLast()`. Это способ явно расположить null; реализация и допустимые SQL-конструкции зависят от диалекта. Для обычного обязательного `id` такой выбор не нужен.

## Offset: перейти на известную страницу

```kotlin
val pageNumber = 2
val pageSize = 10
val page = db.post.findMany {
    orderBy { id.asc() }
    take = pageSize
    skip = (pageNumber - 1) * pageSize
}
```

Вторая страница пропускает первые десять строк и возвращает следующие десять, если они есть. В приложении проверь, что номер страницы положительный, а размер ограничен. Не доверяй произвольному размеру из запроса пользователя.

Offset удобен для перехода по номерам. На глубоких страницах база всё равно должна обработать пропущенный участок. Вставки и удаления между запросами могут сдвинуть страницы даже при стабильном `orderBy`: сортировка не фиксирует снимок данных между двумя HTTP-запросами.

## Cursor: продолжить после ключа

```kotlin
val firstPage = db.post.findMany {
    orderBy { id.asc() }
    take = 10
}
val lastId = firstPage.lastOrNull()?.id
val nextPage = if (lastId == null) {
    emptyList()
} else {
    db.post.findMany {
        cursor(id = lastId)
        take = 10
    }
}
```

Первая выборка идёт по ключу вверх. Следующая продолжает после последнего `id`, исключая саму строку курсора. `inclusive = true` включает её повторно, если это нужно твоему сценарию.

Курсор использует первичный ключ. Для составного ключа нужны все части, а диалект должен поддерживать соответствующее сравнение. В запросе с `cursor` **нельзя задавать явный `orderBy`**: текущий planner отклоняет такое сочетание. Если нужна сортировка по просмотрам и `id`, используй offset либо собственный проверенный SQL с условием продолжения.

Cursor не делает запрос автоматически быстрым при любой схеме: оцени индекс, фильтры и план. Он также не сохраняет неизменный снимок базы между страницами.

## Проекции: получить только нужные поля

```kotlin
val choices = db.user.projectMany {
    select { id; email }
    orderBy { id.asc() }
    take = 20
}
choices.forEach { choice -> println("${choice.id}: ${choice.email}") }
```

Возвращаются `UserProjection`, а не полные сущности. У проекции есть сгенерированные getters всех скалярных полей, но чтение неполученного поля вызывает `VolanFieldNotSelectedException`. Компилятор не создаёт отдельный класс для каждой комбинации select.

`projectFirst` возвращает одну проекцию или null. Проекцию не объединяют с include в одном запросе. Для HTTP-ответа переложи полученные поля в свой DTO и не передавай объект сериализатору, который может обратиться ко всем getters.

## Distinct: уникальные значения колонок

```kotlin
val authors = db.post.projectMany {
    select { authorId }
    distinct { authorId }
}
val authorIds = authors.map { it.authorId }
```

Это список различных `authorId`, а не список публикаций. В SQLite, MySQL и MariaDB набор select должен точно соответствовать distinct-колонкам. PostgreSQL и H2 также допускают выбор представляющей строки; этот вариант не переносится на остальные провайдеры. Когда нужен подсчёт по авторам, используй [groupBy](/next/ru/querying/aggregation), чтобы прямо выразить ожидаемый результат.
