Обновление состоит из двух независимых частей: `where` выбирает строки, `data` задаёт новые значения. Сначала определи, какую запись пользователь вправе изменить, затем передай только те поля, которые действительно нужно заменить.

Ниже используются открытый клиент `db` и [схема User/Post](/next/ru/schema). Чтобы пример был самостоятельным, сначала создаётся тестовый пользователь с новым email. На рабочей базе подставляй проверенный ключ из приложения вместо создания учебной записи.

## Измени имя конкретного пользователя

<CodeGroup>
```kotlin Kotlin
val created = db.user.create { email = "edit@example.org"; name = "Before" }
val updated = db.user.update {
    where { id eq created.id }
    data { name = "After" }
}
println(updated.name)
```

```java Java
var created = db.getUser().create(data -> {
    data.setEmail("edit@example.org");
    data.setName("Before");
});
var updated = db.getUser().update(q -> {
    q.where(w -> w.getId().eq(created.getId()));
    q.data(data -> data.setName("After"));
});
System.out.println(updated.getName());
```
</CodeGroup>

Фильтр указывает первичный ключ, поэтому совпадает максимум одна строка. Изменяется только имя: email остаётся прежним. Метод возвращает обновлённого `User`. Если строки нет, возникает `VolanNotFoundException`; это отличается от массового метода, который вернёт ноль.

## Широкий фильтр не ограничивается одной строкой

<Warning>
В PostgreSQL и SQLite `update` с неуникальным `where` меняет все совпавшие строки и возвращает одну. Без `where` защитного условия нет. Для адресного изменения используй полный ключ, для набора строк — `updateMany` с проверкой количества.
</Warning>

H2 использует возвращающий строки путь. В MySQL и MariaDB путь без RETURNING проверяет выбранные строки и отклоняет несколько совпадений. Это различие диалектов, а не переносимая защита: всегда задавай корректный ключ.

Название `update` само по себе не является проверкой безопасности. В сервисе добавь нужный tenant или owner в условие вместе с ключом. Volan не подставляет такие условия автоматически.

## Пропущенное поле и явный null

```kotlin
val created = db.user.create { email = "clear@example.org"; name = "Alice" }
val cleared = db.user.update {
    where { id eq created.id }
    data { name = null }
}
println(cleared.name)
```

Имя очищено, а email сохранён. Если убрать присваивание name, поле не будет очищено. Это различие особенно важно для PATCH: nullable в запросе и отсутствие параметра не должны сливаться в одну операцию.

Свойства `@updatedAt` runtime обновляет при типизированной записи. Обычные default не применяются заново при каждом update. Ручной SQL нужно поддерживать отдельно, если он должен соблюдать те же правила timestamp.

## Измени набор строк и проверь количество

```kotlin
val affected = db.user.updateMany {
    where { name.isNull() }
    data { name = "Unnamed" }
}
println("Updated rows: $affected")
```

Здесь все пользователи без имени получают значение `Unnamed`. Результат — `Long` с количеством затронутых строк. Если отсутствующих имён нет, вернётся `0L`, без `VolanNotFoundException`.

Перед массовой операцией полезно прочитать или посчитать выборку с тем же условием на тестовой базе. Это помогает увидеть объём, но не фиксирует его между двумя командами при конкурентных изменениях. Когда проверка и запись должны иметь общую границу, используй [транзакцию](/next/ru/transactions) и подходящие правила изоляции своей БД.

## Не потеряй конкурентное изменение

Простой update заменяет значение. Если два запроса прочитали одно состояние и записали свои варианты, последний может перезаписать результат первого. Сам DSL не добавляет optimistic locking.

Для обнаружения конфликта можно спроектировать колонку версии и включить ожидаемую версию в условие `updateMany`, увеличив её в новой data-форме. Возвращённый ноль тогда требует обработки как конфликт или отсутствия — согласно правилам приложения. Это прикладной протокол, а не встроенная автоматическая возможность.

Изменение связанных записей описано в [вложенных операциях](/next/ru/writing/nested-writes). Для удаления отдельная страница объясняет [возвращаемые данные и cascade](/next/ru/writing/delete).
