Ограничения полезно знать до того, как они станут частью архитектуры. Volan находится в alpha: часть форм запросов ещё не поддерживается, а отдельные возможности доступны только в исходниках alpha.3. На этой странице собраны случаи, которые требуют другого решения в приложении.

## Запросы и результаты

| Сценарий | Текущая граница | Что делать |
|---|---|---|
| Cursor с произвольным `orderBy` | Такая комбинация запрещена | Используй offset для нужного порядка или обход по первичному ключу |
| Top-N детей для каждого родителя в include | `take` ограничивает связанный batch | Для гарантированного отдельного лимита запрашивай детей явно |
| Проекция с произвольным набором полей | Один generated projection class | Читай только выбранные поля и собирай явный DTO |
| Чтение незагруженной связи | Getter вызывает исключение | Добавь include либо убери связь из ответа |
| Конкурентный upsert | Find/create-or-update, без атомарного server upsert | Сохрани unique constraint и обрабатывай конфликт |
| Фильтры и сортировки скалярных массивов | Отложены | Измени модель запроса или используй проверенный raw SQL |
| Типизированный full-text поиск | Не реализован | DDL индекса не означает наличие query API |

## Запись связей

Nested writes удобны для небольшого связанного создания, но не выражают любой граф изменений. Ограничены nested update глубже одного уровня связей, удаление owning-side required relation и записи с неизвестным ключом прародителя.

Для сложной операции раздели шаги и выполни поддерживаемые записи через [транзакцию](/next/ru/transactions). Так порядок получения ключей и обновления строк будет виден в коде. Для обязательной связи удаление или disconnect должно сохранять правило схемы: дочерняя строка не может остаться без required parent.

## Имена и схема

Поле `count` конфликтует с агрегатами. Kotlin keywords экранируются не во всех формах generated API. Выбирай безопасное имя клиента и сохраняй SQL-имя через `@map`, когда база уже существует.

Multi-schema models, optimistic `@version` locking, read replicas и sharding сейчас не реализованы. Tenant isolation и soft delete требуют явных условий приложения. QueryInterceptor наблюдает statements и не добавляет эти правила автоматически.

## СУБД и миграции

Интроспекция работает с представимыми структурами и отказывает, если не может сохранить их корректно. Expression/partial indexes, triggers, generated columns, неподдерживаемые таблицы и другие определения могут блокировать pull или планирование. У конкретного provider есть дополнительные [ограничения типов и каталогов](/next/ru/databases).

DDL H2/MySQL/MariaDB делает implicit commit. Журнал сохраняет прогресс, но не превращает весь файл в откатываемую транзакцию. При сбое нужен анализ фактической базы и [ручное восстановление](/next/ru/migrations). Для PostgreSQL/SQLite действуют описанные transactional гарантии, но они не отменяют необходимость проверить SQL и данные перед deployment.

## Async и совместимость

R2DBC отсутствует: JDBC занимает worker и через futures, и через корутины. Отмена активного statement в alpha.3 — запрос драйверу, а не жёсткий дедлайн и не отмена уже завершённого commit. Правила подробно разобраны в [Async](/next/ru/async).

Реализованная возможность в исходниках не означает, что alpha.3 опубликована. Для нового приложения выбирай [совместимый набор версий](/next/ru/versions), а при обновлении повторяй генерацию и проверку на целевой БД. API до 1.0 может меняться; production stability и 100% coverage не обещаны.
