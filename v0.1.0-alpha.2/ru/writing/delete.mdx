Удаление меняет не только список, который видит пользователь. У строки могут быть зависимые записи, а внешний ключ может запретить команду или удалить детей через cascade. Перед выбором метода определи область удаления и правила связей.

Примеры предназначены для тестовой базы с открытым `db` и [схемой User/Post](/v0.1.0-alpha.2/ru/schema). В ней удаление пользователя удаляет его публикации через `onDelete: Cascade`. Не запускай учебную массовую операцию на рабочей базе.

## Удали конкретного пользователя

<CodeGroup>
```kotlin Kotlin
val created = db.user.create { email = "remove@example.org" }
val deleted = db.user.delete {
    where { id eq created.id }
}
println("Deleted user: ${deleted.email}")
```

```java Java
var created = db.getUser().create(data -> data.setEmail("remove@example.org"));
var deleted = db.getUser().delete(q -> {
    q.where(w -> w.getId().eq(created.getId()));
});
System.out.println("Deleted user: " + deleted.getEmail());
```
</CodeGroup>

Метод возвращает скалярные данные удалённого пользователя. Это подтверждение выполненной команды, а не объект, который всё ещё существует в базе. Связи автоматически не загружаются в возвращаемую сущность.

Если ключ не найден, возникает `VolanNotFoundException`. Для сценария «удалить, если существует» можно использовать `deleteMany` с полным ключом и обработать результат `0L` или `1L` по правилам приложения.

## Зафиксируй область удаления

<Warning>
В PostgreSQL и SQLite `delete` с широким фильтром удаляет все совпавшие строки, хотя возвращает одну. Без `where` нет автоматической защиты от удаления всей таблицы. Для одной записи передавай полный первичный или уникальный ключ и нужные условия доступа.
</Warning>



Запрос не добавляет tenant isolation, soft delete и проверку владельца. Если удаление разрешено только владельцу, это должно быть выражено в доступе приложения и фильтре.

## Удали набор и получи количество

```kotlin
val deletedCount = db.user.deleteMany {
    where { email endsWith "@temporary.example.org" }
}
println("Deleted users: $deletedCount")
```

В тестовой базе команда удаляет пользователей с этим окончанием email. Результат — `Long`; отсутствие совпадений даёт ноль. Метод не возвращает список удалённых объектов, поэтому необходимые данные для архива или аудита нужно предусмотреть до удаления и согласовать с транзакцией.

Счётчик относится к строкам команды для этой модели. Не трактуй его как полное число всех зависимых строк, удалённых внешними ключами. Пользователи и их публикации — разные таблицы.

## Cascade, SetNull и запрет удаления

В [схеме связей](/v0.1.0-alpha.2/ru/schema/relations) `Cascade` означает удаление зависимых строк силами базы. `SetNull` сохраняет ребёнка и обнуляет nullable-ключ. `Restrict` / `NoAction` могут отклонить удаление, пока существуют ссылки.

Эти правила определяются структурой БД. Include не управляет cascade: даже незагруженные публикации могут быть удалены. Если данные требуется сохранить, измени правило модели и подготовь миграцию, а не рассчитывай на то, что клиент не запрашивал детей.

## Физическое удаление и soft delete

`delete` и `deleteMany` выполняют физическое удаление. Если приложение хранит историю через `deletedAt`, это обычное поле твоей модели: установи его через update и явно исключай отмеченные строки в чтениях. Volan не превращает delete в soft delete и не добавляет такой фильтр ко всем репозиториям.

Когда удаление входит в несколько согласованных действий с БД, используй [транзакцию](/v0.1.0-alpha.2/ru/transactions). Внешнее уведомление выполняй после успешного завершения: HTTP-запрос не откатится вместе с SQL.
