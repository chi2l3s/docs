Автор и его первая публикация должны появиться вместе. Если вставка публикации не удалась, оставлять частично выполненный сценарий обычно не нужно. Вложенный create выражает обе записи как одну операцию, а runtime выполняет их транзакционно.

Примеры используют открытый `db` и созданные таблицы [User/Post](/v0.1.0-alpha.2/ru/schema). Повторяй их в новой тестовой базе: демонстрационные email уникальны. Несколько SQL-команд внутри одной транзакции не означают один SQL-запрос.

## Создай родителя и ребёнка

<CodeGroup>
```kotlin Kotlin
val author = db.user.create {
    email = "author@example.org"
    posts.create { title = "First post" }
    posts.create { title = "Second post" }
}
val loaded = db.user.findUniqueOrThrow {
    where { id eq author.id }
    include { posts { orderBy { id.asc() } } }
}
println(loaded.posts.map { it.title })
```

```java Java
var author = db.getUser().create(data -> {
    data.setEmail("author@example.org");
    data.getPosts().create(post -> post.setTitle("First post"));
    data.getPosts().create(post -> post.setTitle("Second post"));
});
var loaded = db.getUser().findUniqueOrThrow(q -> {
    q.where(w -> w.getId().eq(author.getId()));
    q.include(i -> i.posts());
});
System.out.println(loaded.getPosts().size());
```
</CodeGroup>

Runtime получает выданный ключ пользователя и подставляет его в `Post.authorId`. Поэтому во вложенном блоке достаточно обязательного заголовка; просмотры получат default. Созданная связь не считается автоматически загруженной на возвращённом `author`: отдельный запрос с include показывает её содержимое.

Без ручного `db.transaction` родитель и вложенные записи всё равно имеют транзакционную границу. Если операция выполняется внутри уже открытой транзакции, она участвует в её правилах; внешний commit нужен для окончательного сохранения.

## `connect`: используй существующую строку

```kotlin
val existingAuthor = db.user.create { email = "existing-author@example.org" }
val post = db.post.create {
    title = "Connected post"
    author.connect { id eq existingAuthor.id }
}
println(post.authorId)
```

`connect` ищет нужного автора и устанавливает связь. Используй условие по полному ключу, которое однозначно выбирает строку. Сам `User` от этого не получает новые имя или email. Для связи многие ко многим подключение создаёт связь через join-таблицу, а не колонку автора.

Отсутствующий target приводит к ошибке и откату операции. Если ключ автора уже известен и дополнительный поиск не нужен, можно передать скалярный `authorId` в обычный create; внешнее ограничение БД всё равно должно проверять существование автора.

## `connectOrCreate`: найди по ключу или вставь

```kotlin
val post = db.post.create {
    title = "Shared author"
    author.connectOrCreate {
        email = "shared-author@example.org"
        name = "Shared author"
    }
}
println(post.authorId)
```

Данные должны покрывать хотя бы один уникальный ключ связанной модели. Здесь таким ключом является email. Если автор найден, переданное имя не обновляет существующую запись. Если не найден, создаётся новый пользователь с этими данными.

Операция выбирает первый полностью покрытый уникальный ключ из metadata модели. Не задавай противоречивые значения нескольких ключей в надежде на отдельное условие поиска: API принимает create-форму и выводит ключ из неё.

Поиск с последующей вставкой не устраняет гонку двух запросов. Unique constraint может отклонить конкурирующую вставку; обработай конфликт по правилам приложения. Транзакционная атомарность одной операции отличается от обещания, что конфликтов никогда не будет.

## Измени уже связанные строки

```kotlin
val author = db.user.create {
    email = "nested-edit@example.org"
    posts.create { title = "Before" }
}
db.user.update {
    where { id eq author.id }
    data {
        posts.update {
            where { title eq "Before" }
            data { title = "After" }
        }
    }
}
```

Вложенный фильтр применяется к публикациям, связанным с этим автором. Здесь меняется их заголовок. Несколько совпадений внутри списочной связи могут означать несколько обновлений; не считай вложенное `update` выбором одной строки по имени метода.

В update-форме набор доступных операций зависит от связи. Отсоединение возможно, когда допустим nullable-внешний ключ или есть join-таблица. Обязательную связь нельзя просто очистить, поэтому `disconnect` для неё не генерируется. `set` заменяет набор связей и не означает удаление целевых строк. Глубокая вложенность update больше одного уровня ограничена.

## Когда лучше явная транзакция

`createMany` не поддерживает вложенные writes. Для большого импорта передавай ключи явно и разделяй задачи по нужным пакетам. Если требуется несколько независимых операций, сложное ветвление или неподдерживаемая глубина изменения связей, [транзакция](/v0.1.0-alpha.2/ru/transactions) делает порядок действий явным.

При ошибке дай исключению выйти из транзакционного callback, если ожидается откат. Письма, HTTP-вызовы и другие внешние действия выполняй после успешного завершения базы.
