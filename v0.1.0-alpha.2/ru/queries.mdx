Запрос начинается с репозитория модели: `db.user` в Kotlin или `db.getUser()` в Java. Репозиторий принимает описание операции, строит SQL и возвращает записи, проекции или число затронутых строк. Тебе не нужно собирать имена колонок строками для обычных операций.

Примеры используют [схему User/Post](/v0.1.0-alpha.2/ru/schema). `db` означает уже открытый клиент, а таблицы должны существовать. Каждый блок ниже показывает операцию внутри приложения; создание клиента и таблиц полностью разобрано в [Первом запросе](/v0.1.0-alpha.2/ru/quickstart).

## CRUD

```kotlin
val created = db.user.create { email = "alice@example.org"; name = "Alice" }
val users = db.user.findMany {
    where { email endsWith "@example.org" }
    orderBy { id.asc() }
    take = 20
    skip = 0
}
db.user.update {
    where { id eq created.id }
    data { name = null }
}
val affected = db.user.updateMany {
    where { name.isNull() }
    data { name = "Unnamed" }
}
db.user.delete { where { id eq created.id } }
```

```java
var users = db.getUser().findMany(q -> {
    q.where(w -> w.getEmail().endsWith("@example.org"));
    q.orderBy(o -> o.getId().asc());
    q.setTake(20);
});
db.getUser().createMany(many -> {
    many.row(d -> d.setEmail("one@example.org"));
    many.row(d -> d.setEmail("two@example.org"));
});
```

`findMany` возвращает список, `findFirst` и `findUnique` — nullable-запись. Варианты `OrThrow` выбрасывают `VolanNotFoundException`. `create`, `update` и `delete` возвращают запись; для `update` и `delete` задай фильтр по первичному или уникальному ключу. Имя метода не гарантирует, что широкий фильтр изменит только одну строку. `createMany`, `updateMany`, `deleteMany` возвращают число затронутых строк. Массовая вставка сохраняет defaults пропущенных полей и объединяет все пакеты строк одной транзакцией.

`upsert { where { ... }; create { ... }; update { ... } }` использует find/create-or-update. Это не атомарный server upsert: конкурентные вставки могут столкнуться с unique constraint.

## Результаты методов

В таблице `User` — сгенерированная сущность, `UserProjection` — проекция выбранных колонок. Это типы результата; имена меняются вместе с моделью схемы.

| Метод | Результат Kotlin | Если совпадений нет |
| --- | --- | --- |
| `findMany` | `List<User>` | Пустой список |
| `findFirst`, `findUnique` | `User?` | `null` |
| `findFirstOrThrow`, `findUniqueOrThrow` | `User` | `VolanNotFoundException` |
| `projectMany` | `List<UserProjection>` | Пустой список |
| `projectFirst` | `UserProjection?` | `null` |
| `count` | `Long` | `0L` |
| `exists` | `Boolean` | `false` |
| `update`, `delete` | `User` | `VolanNotFoundException` |
| `updateMany`, `deleteMany` | `Long` | `0L` |

В Java nullable-результат тоже может быть `null`; `Long`-счётчики здесь соответствуют `long`. Проверяй отсутствие строки до чтения её свойств.

`findUnique` использует тот же путь чтения первой строки, что `findFirst`. Он не проверяет, что `where` описывает уникальный ключ, и не сообщает о нескольких совпадениях. Уникальность должна следовать из твоего условия и ограничений БД: `id eq userId` либо равенство по полному уникальному ключу. `OrThrow` меняет только поведение при отсутствии строки.

<Warning>
Для `update` и `delete` используй ключ конкретной строки. В PostgreSQL и SQLite SQL изменяет все строки, подходящие под `where`, а метод возвращает одну из них. Отсутствующий `where` не добавляет защитного условия. Если нужно изменить набор строк, используй `updateMany` или `deleteMany` и проверь возвращённое количество.
</Warning>

`findMany` без `take` не получает ограничение размера автоматически. Отсутствующий `where` означает все строки; отсутствие `orderBy` не задаёт стабильного порядка. Эти значения удобны для небольшого примера, но лимит страницы и условия доступа задаёт приложение.

## Фильтры

Скалярные поля предоставляют `eq`, `notEq`, `gt`, `gte`, `lt`, `lte`, `oneOf`, `notOneOf`. Для строк доступны `contains`, `startsWith`, `endsWith` и `ignoringCase()`. Nullable-поля поддерживают `isNull()`, `isNotNull()`. Условия группируются через `and`, `or`, `not`. В Java используются getters и методы: `w.getId().eq(1)`, `w.or(o -> { ...; })`.

Значения передаются параметрами. В raw SQL передавай их списком parameters; не вставляй пользовательский ввод в SQL. Регистронезависимое сравнение строк зависит от СУБД; встроенное преобразование SQLite работает с ASCII.

## Пагинация

`take` ограничивает результат, `skip` пропускает строки. Задавай стабильный порядок с уникальным полем для разрешения совпадений. `cursor(id = lastId)` обходит записи по первичному ключу и исключает строку курсора, если не задано `inclusive = true`. Для составного ключа нужны все части. Cursor вместе с явным `orderBy` пока запрещён; для такого порядка используй offset.

## Агрегаты

`count()` и `exists()` не загружают сущности. `aggregate { count(); sum { views }; average { views } }` возвращает агрегаты. `groupBy { by { authorId }; count(); having { count gt 1L } }` — сгруппированные значения. Чтение невыбранных полей вызывает исключение. [Связи](/v0.1.0-alpha.2/ru/relations) объясняют частичные результаты.

## Как выбрать метод чтения

`findUnique` удобен, когда у тебя есть первичный или уникальный ключ: например, пользователь с конкретным `id`. `findFirst` нужен, когда условию могут соответствовать разные строки, а приложение выбирает первую. В этом случае задай порядок, чтобы «первая» запись имела определённый смысл. `findMany` возвращает список, который может быть пустым.

Nullable-результат позволяет нормально обработать отсутствие пользователя: вернуть 404, предложить регистрацию или продолжить без данных. Вариант `OrThrow` подходит для внутренней операции, где отсутствие записи нарушает ожидаемый сценарий. Не подменяй им бизнес-проверку существования, если пустой результат допустим.

## Что делает пример CRUD

Сначала создаётся Alice. Чтение выбирает email с нужным окончанием, сортирует по `id` и ограничивает страницу двадцатью строками. Следующее обновление очищает имя только у созданного пользователя. `updateMany` затем заменяет NULL-имена значением `Unnamed` и возвращает количество изменённых строк. Последнее удаление снова адресовано конкретному `id`.

Фильтр определяет область записи. Перед bulk update или delete проверь, сколько строк соответствует условию, и нужны ли ограничения прав доступа. Tenant-поле и признак soft delete добавляются в `where` явно: runtime не подставляет их за приложение.

## Порядок и размер страницы

Ограничение `take` защищает сервис от чтения всей таблицы, но не делает порядок стабильным. При сортировке по неуникальному полю одинаковые значения должны разрешаться уникальным ключом. Иначе две соседние страницы могут пересекаться или пропускать записи.

Offset удобен для простого списка с номерами страниц, но при больших `skip` база всё равно обрабатывает пропускаемую часть. Cursor предназначен для обхода по первичному ключу; текущий API не разрешает комбинировать его с произвольным `orderBy`. Выбирай способ пагинации под нужный порядок, а не только под внешний вид UI.

## Когда сущности не нужны

Для проверки существования используй `exists`, для количества — `count`. Если HTTP-ответу нужны только email, выбирай проекцию. Агрегаты считают результат на стороне БД, поэтому приложение не обязано загружать все публикации, чтобы сложить их просмотры. Условия relation-фильтра также не загружают саму связь.

## SQL с параметрами

Если нужная операция пока не выражается через репозиторий, используй `rawQuery` для чтения и `rawExecute` для изменения. Следующие фрагменты выполняются внутри приложения с уже открытым `db` и таблицей `User` из [Первого запроса](/v0.1.0-alpha.2/ru/quickstart). В таблице может не быть пользователя с указанным email: тогда результат — пустой список.

```kotlin
val emailToFind = "alice@example.org"
val emails = db.rawQuery(
    """SELECT "email" FROM "User" WHERE "email" = ?""",
    listOf(emailToFind),
) { row -> row.getString("email") }
```

```java
var emailToFind = "alice@example.org";
var emails = db.rawQuery(
    "SELECT \"email\" FROM \"User\" WHERE \"email\" = ?",
    java.util.List.of(emailToFind),
    row -> row.getString("email")
);
```

Один `?` соответствует одному значению в `parameters`, в порядке появления. Параметры передают значения, а не имена таблиц, колонок или направление сортировки. Такие части SQL выбирай из фиксированного набора приложения. SQL выше предназначен для PostgreSQL и SQLite; runtime не переводит произвольный SQL между диалектами.

Mapper вызывается для каждой строки и собирает твой результат; автоматических `include` у raw query нет. `getString` требует значение, отличное от SQL `NULL`, для nullable-колонки используй `getStringOrNull`. Сам `rawQuery` возвращает `List<T>` и не добавляет `LIMIT`: ограничение должно быть в SQL.

`rawExecute(sql, parameters)` возвращает `Long` с количеством затронутых строк. Для DDL это значение зависит от драйвера и не служит количеством созданных таблиц. Эти методы используют текущее соединение внутри `transaction`; несколько вызовов снаружи не образуют одну транзакцию. Сгенерированный клиент должен быть подключён к базе: клиент только над executor не поддерживает raw SQL.
