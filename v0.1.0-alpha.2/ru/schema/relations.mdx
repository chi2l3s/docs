Связь отвечает на вопрос, как записи относятся друг к другу. У публикации есть автор, у пользователя — список публикаций. В схеме ты описываешь обе стороны, но физический внешний ключ хранится только там, где указаны `fields`.

## Один ко многим

Этот фрагмент заменяет модели `User` и `Post` в схеме; настройки `datasource` и `generator` сохраняются:

```prisma
model User {
  id Int @id @default(autoincrement())
  email String @unique
  name String?
  posts Post[]
}

model Post {
  id Int @id @default(autoincrement())
  title String
  views Int @default(0)
  authorId Int
  author User @relation(fields: [authorId], references: [id], onDelete: Cascade)
}
```

`Post.authorId` — обычная колонка. `Post.author` — свойство связи, а `User.posts` — обратный список. Колонка `posts` в таблице `User` не появляется. `fields: [authorId]` задаёт локальный ключ; `references: [id]` — поле назначения.

Типы этих полей должны совпадать. Поля назначения должны образовывать первичный или уникальный ключ, иначе одна ссылка могла бы указывать на несколько пользователей. Для составного ключа перечисляются все части в соответствующем порядке.

## Один к одному

Разница с предыдущим вариантом — уникальность внешнего ключа. Пример отдельной пары моделей:

```prisma
model Account {
  id Int @id @default(autoincrement())
  profile Profile?
}

model Profile {
  id Int @id @default(autoincrement())
  accountId Int @unique
  account Account @relation(fields: [accountId], references: [id], onDelete: Cascade)
}
```

У аккаунта может не быть профиля, поэтому обратная сторона — `Profile?`. Но каждый профиль обязан ссылаться на аккаунт. `@unique` на `accountId` запрещает создавать два профиля одного аккаунта.

## Многие ко многим

Если обе стороны содержат список и ни одна не владеет внешним ключом, Volan описывает неявную таблицу связей:

```prisma
model Article {
  id Int @id @default(autoincrement())
  tags Tag[]
}

model Tag {
  id Int @id @default(autoincrement())
  name String @unique
  articles Article[]
}
```

Один тег может относиться к разным статьям, а у статьи может быть несколько тегов. Если у самой связи нужны поля — например, время добавления или роль участника — опиши отдельную модель-связку с двумя явными отношениями и подходящим составным ключом.

## Несколько связей с одной моделью

Когда две модели связаны несколькими способами, явно дай каждой паре одинаковое имя `@relation("...")` на обеих сторонах. То же нужно для различения ролей в self relation, например руководителя и подчинённых. Имя позволяет анализатору связать правильные поля; оно не заменяет `fields` и `references` у владельца внешнего ключа.

## Что произойдёт при удалении

`Cascade` удаляет зависимые строки силами БД. В первом примере удаление пользователя удалит и его публикации. Это разумно только тогда, когда именно такое правило нужно приложению.

`SetNull` сохраняет зависимую строку, обнуляя её внешний ключ. Для него ключевые поля должны быть nullable. `Restrict` и `NoAction` препятствуют несовместимому удалению; конкретный момент проверки определяет СУБД. `onUpdate` описывает аналогичное действие при изменении ключа назначения. Здесь referential actions задаются явно; не выводи желаемое поведение из названия свойства.

## Определить связь и загрузить связь — разные шаги

После генерации скалярный `authorId` доступен при обычном чтении публикации. Для объекта `author` нужен `include`. Чтение незагруженной связи вызывает `VolanRelationNotLoadedException`, без скрытого SQL. Пустой загруженный список означает, что детей нет; незагруженный список означает, что их не запрашивали.

Продолжи с [загрузкой связей](/v0.1.0-alpha.2/ru/relations) или [вложенными операциями записи](/v0.1.0-alpha.2/ru/writing/nested-writes). После изменения схемы обнови клиент и таблицы перед запуском запросов.
