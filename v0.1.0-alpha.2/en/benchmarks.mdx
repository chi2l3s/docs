A benchmark answers a narrow question: how long a defined operation takes in a defined environment. This suite measures pooled PostgreSQL reads with field materialization. In the recorded run, Volan took longer than the listed alternatives; the table presents that difference directly.

Use these results as a starting point for verification and optimization. They do not predict every application's performance: result sizes, networking, schemas, includes and concurrency change the workload.

| Library | 1 row, µs/op | 100 rows, µs/op |
|---|---:|---:|
| Volan | 2432.5 ± 76.7 | 2640.4 ± 145.4 |
| Hibernate | 1360.0 ± 171.6 | 1504.5 ± 163.3 |
| Exposed | 1791.6 ± 130.0 | 1816.3 ± 84.9 |
| jOOQ | 1233.7 ± 85.0 | 1458.8 ± 153.5 |
| JDBC | 1157.4 ± 44.5 | 1311.5 ± 86.4 |

Means ± JMH 99.9% confidence interval, microseconds per operation; lower is better. Run dated 7 September 2026: Ryzen 5 5500, Windows 11, Corretto 25.0.3, PostgreSQL 17.10 in Docker/WSL2. 10,000 rows, four fields, 1 thread, HikariCP pools of 4.

Each operation constructs the query, borrows a connection, opens a read-committed transaction, materializes all fields and commits. Correctness is checked before timing. Cases read 1 or 100 rows with WHERE id >= ?, ORDER BY id, LIMIT ?. Defaults: 2 JVM forks, 3 × 2 s warmup, 5 × 2 s measurement, 512 MiB heap.

The suite does not measure writes, includes, nested writes, concurrent throughput, migrations, startup or allocations. Loopback networking is included. Results do not establish universal performance or application throughput; compare confidence intervals.

## Reproduce

Java 17+, Docker; Python for reporting. Run from repository root:

```bash
docker compose -p volan-bench -f benchmarks/compose.yaml up -d --wait
export VOLAN_BENCH_URL='jdbc:postgresql://localhost:55432/volan_bench'
./gradlew :benchmarks:jmh
python benchmarks/report.py benchmarks/build/results/jmh.json
docker compose -p volan-bench -f benchmarks/compose.yaml down
```

On PowerShell set `$env:VOLAN_BENCH_URL = 'jdbc:postgresql://localhost:55432/volan_bench'` and use `.\gradlew.bat`. The fixture creates its own database; do not point it at application data.

[Methodology](https://github.com/thirtyeighttwentysix/volan/blob/v0.1.0-alpha.2/benchmarks/README.md), [raw results and machine metadata](https://github.com/thirtyeighttwentysix/volan/tree/v0.1.0-alpha.2/benchmarks/results).

## Read the table

Values are microseconds per operation. For example, `2432.5 µs/op` is about `2.43 ms` for that measured case, not the duration of every Volan query. The interval beside the mean shows measurement uncertainty; a number without its method suggests false precision.

The columns compare one-row and hundred-row reads. They do not establish a linear per-row cost: each operation includes fixed connection, transaction and networking costs. The comparison is for the defined shared work, not every feature each ORM offers.

## Measure your own workload

Reading a user with several relations is outside this benchmark. Build a representative query, fix data volume, pool size and concurrency, check correctness and then measure. Observe physical statements and connection waits separately.

Do not judge from one initial run; JVM and database warmup affect results. Save machine parameters and raw results so later runs can be compared. A faster incorrect result is not a successful optimization.
