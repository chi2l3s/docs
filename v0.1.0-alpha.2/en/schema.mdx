`schema.volan` answers a few concrete questions: which records your application stores, which fields are required, what makes a record unique and how models relate to each other. Volan generates its read and write API from that description.

In the schema below, a user can have many posts and every post has one required author. [Queries](/v0.1.0-alpha.2/en/queries), [Relations](/v0.1.0-alpha.2/en/relations) and [Transactions](/v0.1.0-alpha.2/en/transactions) use this model. When extending the first quickstart, add `Post`, regenerate the client and update the database structure.

```prisma
datasource db {
  provider = "sqlite"
  url = env("DATABASE_URL")
}
generator client {
  provider = "volan-kotlin"
  package = "org.example.generated"
  javaFriendly = true
}
model User {
  id Int @id @default(autoincrement())
  email String @unique
  name String?
  posts Post[]
}
model Post {
  id Int @id @default(autoincrement())
  title String
  views Int @default(0)
  authorId Int
  author User @relation(fields: [authorId], references: [id], onDelete: Cascade)
}
```

## Fields and keys

`String` is required, `String?` nullable, `Post[]` a relation list. Optional lists and nested lists are invalid. Scalars: String, Int, Long, Float, Double, Decimal, Boolean, DateTime, Date, Time, Json, Bytes, Uuid. Supported storage depends on [database](/v0.1.0-alpha.2/en/databases); SQLite rejects Decimal and scalar arrays.

| Attribute | Purpose |
|---|---|
| `@id`, `@@id([a,b])` | Single or composite primary key |
| `@unique`, `@@unique([a,b])` | Unique constraint |
| `@@index([a,b])` | Index |
| `@map("column")`, `@@map("table")` | Keep client names separate from SQL names |
| `@default(...)` | Compatible literal, enum, now(), uuid(), autoincrement() |
| `@updatedAt` | Runtime-maintained timestamp |
| `@relation(...)` | Relation and foreign key |
| `@@ignore` | Omit client for a table without a usable key |

Exactly one primary key is required unless ignored. Foreign key types and referenced unique keys must match. One-to-one foreign keys need a unique constraint. SetNull needs nullable foreign keys. Implicit many-to-many uses paired lists without an owning foreign key.

`@db` native overrides are PostgreSQL-specific. `@@fulltext` does not provide a typed full-text query API. Do not use a scalar named `count` or Kotlin keywords as field names; map a safe alias instead.

## Generation

The matching `volan-codegen:0.1.0-alpha.2` reads and validates the schema, then emits Kotlin. [First query](/v0.1.0-alpha.2/en/quickstart) wires that program into compilation. The alpha.2 database CLI does not generate or format source.

Generation never opens the database. `env("DATABASE_URL")` is resolved by operations that need a connection. `//` comments and `///` documentation survive formatting; block comments are invalid. Field attributes belong on the field's line.

[Complete syntax and diagnostics](https://github.com/thirtyeighttwentysix/volan/blob/v0.1.0-alpha.2/docs/schema-language.md).

## Why a relation has two fields

In `Post`, `authorId` is the scalar foreign key stored in the table. `author` describes the relation in the client API. On the user side, `posts` is the inverse list; it does not become a column in the `User` table.

`fields: [authorId]` identifies the foreign key and `references: [id]` identifies the author's unique target field. With `onDelete: Cascade`, the database foreign key deletes a user's posts when that user is deleted. Choose that behavior to match application rules; keeping posts after user deletion requires a different relation model.

## Required, nullable and defaulted

`email String` has no default, so creating a user requires an email. `name String?` permits SQL NULL. Omitting `views Int @default(0)` lets the database default supply zero. In an update form, leaving a field unassigned means keeping its current value; assigning `name = null` explicitly clears it.

A default is not a business rule. An initial `views = 0` does not prevent an application from writing a negative value. Application validation and database constraints complement the schema types.

## Client and database names

Mapping lets application code use readable names while an existing database keeps its SQL names. `@map` maps a column and `@@map` maps a table; Kotlin and Java use the model names. It also provides a safe alias when a database name conflicts with a generated API name.

Renaming a schema field does not prove that the database needs a rename operation. A sync plan may see a drop followed by an add. To preserve data, prepare and review an explicit SQL rename migration.
