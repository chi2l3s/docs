In a web application, the client outlives a single HTTP request. Create it at startup, inject it into services and close it after active work finishes during shutdown. That avoids creating a connection pool for every endpoint.

Volan currently has no Spring Boot starter or Ktor plugin. Integration uses the framework's regular mechanisms. First configure [client generation](/v0.1.0-alpha.2/en/quickstart) and apply the database structure; the examples below fit that client into the application lifecycle.

## Spring Boot

Register the generated client as a singleton bean. Add runtime, dialect and JDBC driver; run reviewed migrations before serving requests. In an existing Boot application:

```java
package org.example;

import org.example.generated.VolanClient;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration(proxyBeanMethods = false)
public class DatabaseConfig {
    @Bean(destroyMethod = "close")
    public VolanClient volanClient() {
        return VolanClient.builder()
            .url(System.getenv("DATABASE_URL"))
            .username(System.getenv("DATABASE_USER"))
            .password(System.getenv("DATABASE_PASSWORD"))
            .build();
    }
}
```

Constructor-inject VolanClient into a service. A synchronous Spring MVC service can call `db.getUser().count()` on its request worker. For WebFlux, dispatch JDBC to a bounded worker executor; JDBC does not become reactive. Use Volan transaction callbacks; do not assume `@Transactional` automatically joins them.

If Boot already owns a DataSource, use `.dataSource(dataSource).url(jdbcUrl)` to select the dialect. Volan leaves the supplied DataSource open; Boot owns its destruction. Avoid inadvertently creating a second pool. [Spring bean lifecycle](https://docs.spring.io/spring-framework/reference/core/beans/java/bean-annotation.html).

## Ktor

This integration dispatches JDBC with kotlinx-coroutines configured by the application. Set DATABASE_URL to a migrated SQLite file, such as `jdbc:sqlite:./data.db`, and invoke volanModule from the application module.

```kotlin
package org.example

import org.example.generated.VolanClient
import io.ktor.server.application.Application
import io.ktor.server.application.ApplicationStopped
import io.ktor.server.response.respondText
import io.ktor.server.routing.get
import io.ktor.server.routing.routing
import kotlinx.coroutines.Dispatchers
import kotlinx.coroutines.withContext

fun Application.volanModule() {
    val db = VolanClient.builder()
        .url(requireNotNull(System.getenv("DATABASE_URL")))
        .build()
    monitor.subscribe(ApplicationStopped) { db.close() }
    val jdbcWorkers = Dispatchers.IO.limitedParallelism(4)
    routing {
        get("/users/count") {
            val count = withContext(jdbcWorkers) { db.user.count() }
            call.respondText(count.toString())
        }
    }
}
```

GET `/users/count` returns the row count as text. Create the client once when the module starts, not in each route. Align worker concurrency with pool size; SQLite's built-in pool has one connection. The lifecycle hook follows [Ktor events](https://ktor.io/docs/server-events.html). Drain application jobs before closing the client.

## HTTP data

Map rows or projections to DTOs containing explicitly selected scalar fields. Do not serialize generated entities blindly: serializers may read unloaded relations. Translate not-found and constraint failures into application-specific HTTP responses; omit internal SQL and credentials.

## From route to database

The HTTP handler parses and validates input. A service performs the query or transaction and returns the required fields. At the HTTP boundary, those fields become a DTO and a response. This separation lets you test the database operation without running a full web server.

The Ktor route is deliberately small: GET `/users/count` returns a text count. An empty table returns `0`, which is normal. A missing table produces a database exception; client lifecycle setup does not replace migrations.

## Give resources an owner

Close the client when finished if it owns the built-in pool. If Spring Boot created the DataSource, Boot owns its shutdown. A supplied executor likewise belongs to the application. Coordinate shutdown order so active operations can finish before their resources disappear.

A relative SQLite URL depends on the server working directory. Starting from another directory can open a different file and look like missing data. Set the deployment path explicitly and verify which file is in use.

## Transactions and responses

Use `db.transaction` for related database operations. A Spring `@Transactional` annotation alone does not prove that Volan joins the same connection-bound transaction. In Kotlin, move the entire operation to a worker and keep transaction callback queries synchronous.

Map missing rows to endpoint behavior, unique-key violations to understandable data conflicts and temporary unavailability to a suitable service response. Do not return an entire SQL exception to the caller. Keep the cause in application diagnostics and build the response from selected fields.
