Check these boundaries before designing an application around an unsupported operation. This section describes alpha.1; features in development are not part of this runtime.

## Queries and results

| Scenario | Current boundary | Application approach |
|---|---|---|
| Cursor with arbitrary `orderBy` | Combination is rejected | Use offset for that order or traverse the primary key |
| Top-N children for every included parent | `take` limits a related batch | Query children explicitly when a separate per-parent limit is required |
| Arbitrary projection shape | One generated projection class | Access selected fields and build an explicit DTO |
| Accessing an unloaded relation | Getter throws | Add include or omit the relation from the response |
| Concurrent upsert | Find/create-or-update, without atomic server upsert | Keep a unique constraint and handle conflicts |
| Scalar-array filtering and ordering | Deferred | Change the query model or use reviewed raw SQL |
| Typed full-text search | Not implemented | Index DDL does not imply a query API |

## Relation writes

Nested writes support small related operations, but they do not represent every change graph. Nested update beyond one relation level, deleting an owning-side required relation and writes with unknown ancestor keys are restricted.

For a complex operation, split supported writes into explicit steps inside a [transaction](/v0.1.0-alpha.1/en/transactions). Key acquisition and write order then stay visible. Deleting or disconnecting a required relation must preserve the schema rule: a child cannot remain without its required parent.

## Names and schema

`count` conflicts with aggregates. Kotlin keywords are not escaped in every generated API form. Choose a safe client alias and retain the existing SQL name through `@map` when needed.

Multi-schema models, optimistic `@version` locking, read replicas and sharding are not implemented. Tenant isolation and soft delete need explicit application predicates.

## Providers and migrations

Introspection accepts representable structures and refuses definitions it cannot preserve correctly. Expression/partial indexes, triggers, generated columns, unsupported tables and other definitions can block pull or planning. Each provider has further [type and catalog limits](/v0.1.0-alpha.1/en/databases).

PostgreSQL migrations have transactional guarantees described in [Migrations](/v0.1.0-alpha.1/en/migrations). Review SQL and existing data before deployment; a transaction cannot make a logically wrong data change correct.

## Async and compatibility

JDBC remains blocking through futures or framework coroutine dispatch. Alpha.1 future cancellation does not cancel an active JDBC statement. [Async](/v0.1.0-alpha.1/en/async) explains workers and cleanup.

Keep generator and runtime on alpha.1 and regenerate on upgrades. The alpha API can change before 1.0. PostgreSQL is this release's provider; build plugins, H2, MySQL, MariaDB and Volan coroutine/metrics modules belong to later development.

## Fixes in the following release

Alpha.2 fixes bulk insert defaults/order and JDBC relation-key matching. Test heterogeneous createMany input carefully on alpha.1; use per-row creates in one transaction when correctness depends on these cases, or upgrade and regenerate.
