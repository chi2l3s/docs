The CLI built from `v0.1.0-alpha.1` is a database synchronization tool. It provides `db pull` and `db push`, and needs Java 17+. [Installation](/v0.1.0-alpha.1/en/installation) shows how to build the tagged tool and put its launcher on PATH.

```bash
volan --help
volan db pull --url jdbc:postgresql://localhost:55433/volan_example --stdout
volan db push --schema schema.volan --url jdbc:postgresql://localhost:55433/volan_example --dry-run
volan db push --schema schema.volan --url jdbc:postgresql://localhost:55433/volan_example
```

## Read before changing

`pull --stdout` prints the representable database structure. Without stdout, pull writes the schema file; `--force` allows replacing an existing file. Save introspection to a separate file first so it cannot replace your intended model accidentally.

`push --dry-run` prints SQL and warnings without applying the plan. Run it against the intended development database and review drops, new required fields and constraints. `--accept-data-loss` accepts warning-bearing changes; it does not make them reversible.

## Connection and paths

The default schema path is `schema.volan`. Push uses its datasource URL unless `--url` overrides it. Pull uses `--url` or `DATABASE_URL`. For PostgreSQL, provide `DATABASE_USER` and `DATABASE_PASSWORD` through the environment.

URLs use JDBC syntax. Check the target before applying a plan. [Schema sync](/v0.1.0-alpha.1/en/sync) explains comparison direction and introspection limits.

## Commands in this release

Alpha.1 does not include `init`, `generate`, `format`, `validate`, `migrate` or `--resolve`. Generate the client with the alpha.1 build program from [First query](/v0.1.0-alpha.1/en/quickstart). Apply versioned migration files through the [migration API](/v0.1.0-alpha.1/en/migrations).

The alpha.3 preview CLI has a larger command set and newer generated APIs. Selecting its documentation does not update your application dependencies. Use the tool and generator that match your application release.

## Database URL precedence

For `db push`, the order is:

1. An explicit `--url`.
2. The schema datasource URL: a literal, or the value of the variable named in `env(...)`.
3. `DATABASE_URL`, if the earlier sources provide no value.

`db pull` does not load an existing schema to choose its connection. It uses `--url`, then `DATABASE_URL`; `--schema` names the output file. If your datasource uses `env("APP_DATABASE_URL")`, pull still needs `--url` or `DATABASE_URL`.

An empty string is not a missing value: a selected empty URL does not fall back to the next source and fails JDBC URL validation. `DATABASE_USER` and `DATABASE_PASSWORD` are passed separately to the driver. A schema's env declaration also does not make the application client builder read its URL automatically.

## Output and file writes

| Mode | stdout | Files and database |
| --- | --- | --- |
| `db pull --stdout` | Schema text | Does not write the schema file |
| `db pull` | `Wrote ...` after success | Creates a new file; preserves an existing file without `--force` |
| `db push --dry-run` | Plan SQL or `Schema is up to date.` | Does not apply the plan; connects to the database |
| `db push` | Change count or `Schema is up to date.` | Applies the plan when its checks pass |

Dry-run warnings go to stderr, separately from SQL. Exit code zero means command success, not necessarily a change: an empty drift plan also succeeds. In CI, treat a nonzero exit as failure and retain stderr rather than inferring success from a stdout message.

`--force` permits replacing a pull output file. `--accept-data-loss` permits applying a warning-bearing plan. They belong to different operations; neither is a general ignore-errors mode.
