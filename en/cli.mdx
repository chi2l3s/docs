title: "CLI"
description: "Validate and format schemas, generate clients and run explicit database operations."

Use the CLI when schema work should be a separate, inspectable step: before a commit, in CI or while connecting an existing database. It reads `schema.volan`, reports diagnostics and performs the operation you request.

It needs Java 17+. [Install it](/en/installation), then check [generator compatibility](/en/versions). The current preview generates the alpha.3 API and cannot replace the generator in an alpha.2 application build.

```bash
volan --help
volan init --provider sqlite --package example.generated --java-friendly
volan validate --schema schema.volan
volan format --schema schema.volan --check
volan generate --schema schema.volan --output build/generated/volan
volan db push --schema schema.volan --url jdbc:sqlite:./data.db --dry-run
volan db pull --url jdbc:sqlite:./data.db --stdout
```

| Command | Options | Result |
|---|---|---|
| init | --schema, --provider, --package, --java-friendly | Create schema; refuse overwrite |
| validate | --schema | Syntax and semantic diagnostics |
| format | --schema, --check, --stdout | Format, compare or print |
| generate | --schema, --output | Generated Kotlin and ownership manifest |
| db pull | --schema, --url, --stdout, --force | Introspect database |
| db push | --schema, --url, --dry-run, --accept-data-loss, --resolve | Plan, apply or verify repaired push |

Defaults: schema path `schema.volan`, init provider `postgresql`, package `com.example.volan`, Java callbacks disabled unless `--java-friendly`.

Format checks syntax; validate also checks semantics. `--check` and `--stdout` are mutually exclusive. Format check exits nonzero on differences and changes no file. Generation resolves output relative to the current project directory, validates the schema and does not open a database.

Database URL must use JDBC syntax; URL/provider consistency matters. DATABASE_USER and DATABASE_PASSWORD supply server credentials. Never put real secrets in schema or command examples. `--resolve` and `--dry-run` cannot be combined.

Read [Schema sync](/en/sync) and [Migrations](/en/migrations) before applying changes. There are no migrate, studio, self-update or native-image CLI commands. init does not create a Gradle or Maven project.

## A regular schema workflow

After changing a model, run `validate`: formatted text can still contain an invalid relation or key. Run `format --check` to verify shared formatting before a commit. Both commands can run without a database connection.

Generation updates the client API and compilation checks its uses. If generation is wired into the build, a separate manual `generate` is usually unnecessary. Database changes are another step: inspect a plan or dry-run, then apply reviewed changes.

## Commands in CI

`format --check` leaves the file unchanged and exits unsuccessfully when formatting differs, making it useful as a check. `--stdout` prints formatting or pull output for inspection or external saving; it cannot be combined with `--check`.

Pin the CLI or codegen version alongside the runtime for generation. Updating a system executable then cannot unexpectedly change a build's generated API. Schema checks and compilation need no credentials; only commands that access the database need them.

## Explicit paths and database targets

Paths are resolved from the current directory. Pass `--schema` explicitly when running elsewhere and check the output location. SQLite JDBC file paths are relative too. Before push, verify that the command points at the intended development database.

SQL plans and recovery are explicit database operations, described in [Schema sync](/en/sync) and [Migrations](/en/migrations).
