---
title: "Migrations"
description: "Update database structure with reviewed SQL files and a recorded application history."
---

A migration ties a model change to concrete SQL your team can review, commit and apply during deployment. With existing data, adding a field or changing a key must account for stored rows as well as the new schema.

`Migrator` reads migration directories, checks the recorded history and applies new files. Its API needs `volan-migrate` on the runtime version. There is currently no `volan migrate` CLI command.

## Create and apply

Use the schema and sync from [Schema sync](/en/sync); set `url = "jdbc:sqlite:./data.db"`. Plan against the database version preceding this migration, not one already changed by push.

```kotlin
import io.github.thirtyeighttwentysix.volan.migrate.MigrationDirectory
import io.github.thirtyeighttwentysix.volan.migrate.Migrator
import java.nio.file.Path
import java.time.Instant
import java.sql.DriverManager

val directory = MigrationDirectory(Path.of("migrations"))
DriverManager.getConnection(url).use { connection ->
    val plan = sync.plan(connection, schema)
    if (!plan.isEmpty) {
        println(plan.warnings)
        directory.write(Instant.now(), "add_posts", plan.toSql(SqliteDialect))
    }
}
// Review and commit migrations/*/migration.sql before deployment.
DriverManager.getConnection(url).use { connection ->
    Migrator(directory).apply(connection)
}
```

Folders are `yyyyMMddHHmmss_description/migration.sql`. Names cannot overwrite existing migrations. SHA-256 checksums normalize CRLF to LF. Retain reviewed files unchanged after deployment.

`Migrator.status(connection)` reports applied, pending, edited, missing and unfinished entries. Apply refuses inconsistent history. `markApplied(connection, migration)` records a reviewed existing baseline or completed repair; it executes no SQL and is not a structural verification.

## PostgreSQL and SQLite

Each file and journal entry commit together; failure rolls back. Dedicated connections must begin in auto-commit mode. PostgreSQL advisory locks serialize Volan writers in the current schema. SQLite uses BEGIN IMMEDIATE, rechecks history after acquiring the lock and checks foreign keys before commit. Table rebuilds retain surviving data and AUTOINCREMENT history. A required new column without a default can fail on populated tables.

Scripts must not contain their own transaction control. PostgreSQL CREATE INDEX CONCURRENTLY is outside the transactional migrator. Adding an enum value and using it may require separate commits/migrations.

## H2, MySQL, MariaDB

These providers require alpha.3. DDL has implicit commit. H2 acquires exclusive mode; use a maintenance window, a dedicated administrator connection and no outstanding application transactions. MySQL/MariaDB acquire a database-specific named session lock, waiting up to 60 seconds. Locks coordinate Volan writers, not unrelated application SQL or other tools.

The journal commits a start record, acknowledges each completed statement in `applied_steps`, then sets `finished_at`. Failure leaves committed steps and an unfinished record. Further apply stops; partial scripts are never replayed automatically. After a crash, the acknowledged count is only a lower bound: another statement may already have committed.

## Recovery

1. Stop competing schema/application writes. Retain the original SQL and checksum.
2. Read status/journal and inspect the actual database. Compare with the intended final structure.
3. Manually complete or repair the changes, or restore a consistent backup.
4. Once the intended state exists, finish the original record:
```kotlin
val original = directory.read().single { it.id == failedMigrationId }
DriverManager.getConnection(url).use { connection ->
    val migrator = Migrator(directory)
    migrator.markApplied(connection, original)
    migrator.apply(connection)
}
```

Do not edit a partially applied script or delete its journal to force replay. markApplied preserves original checksum, start and acknowledged progress; it trusts your repair.

An unfinished push uses `_volan_push` and blocks push/versioned apply. Repair to the original target, then run:
```bash
volan db push --schema schema.volan --url jdbc:h2:file:./data --resolve
```

`sync.resolvePush(connection, originalSchema)` is the library equivalent. It checks the original target fingerprint and actual structure, performs no repair DDL and refuses a changed/incomplete target.

Reserve `_volan_push` and `_volan_migrations`. Push interlocks with the default versioned journal; custom journal users must coordinate unfinished states themselves. Nontransactional scripts must not change session, transaction, schema/database or locking state, directly or through routines. Executable MySQL/MariaDB version comments are refused.

[Detailed script restrictions and recovery](https://github.com/thirtyeighttwentysix/volan/blob/main/docs/migrations.md).

## Change a database with existing rows

Consider a user table that already contains rows and a new required field. Adding NOT NULL without a suitable default can fail because the database has no value for existing users. Decide how to populate old rows, then prepare SQL and verify the result.

For a column rename, do not rely on schema comparison inferring the intent: it may look like a drop and an add. Test the migration against the previous structure with representative data. An empty database does not reveal every transition problem.

## Why the file stays unchanged

A checksum links the journal entry to migration text. Editing a file after it ran in one environment can produce different structures under the same identifier. Usually, fix an applied migration with a new file and keep the original in history.

`edited` means local text differs from the applied file; `missing` means an applied file is absent from the directory; `unfinished` requires inspecting an interrupted run. Do not hide these states by deleting journal entries. Establish how history and actual database state differ first.

## Plan deployment

Run migrations on a dedicated connection before starting code that needs the new structure. For multiple application instances, choose who applies them. A dedicated deployment task is often easier to control than concurrent migration attempts during every instance startup.

A lock coordinates Volan writers within the documented scope. It does not prevent manual DDL from another tool. Coordinate team and process activity during complex changes. For H2/MySQL/MariaDB, allow time to inspect partial progress and recover.

## What markApplied means

This operation records your assertion that the migration already reached its intended state. It neither executes skipped SQL nor proves table correctness. Use it only after checking actual structure and data against the original goal. Partial push uses a separate `resolvePush` operation that checks structure and target fingerprint; the two mechanisms solve different problems.
