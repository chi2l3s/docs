На экране профиля нужны и пользователь, и его публикации. В списке пользователей публикации могут быть лишними. Volan позволяет выразить этот выбор в запросе: `include` загружает связь, а без него результат содержит скалярные поля модели.

Примеры используют [схему User/Post](/ru/schema). Здесь `posts` — связь пользователя с публикациями, а `email` — обычная колонка. Для отдельных колонок есть `projectMany` и `projectFirst`: они возвращают сгенерированную проекцию.

```kotlin
val loaded = db.user.findMany {
    include { posts { orderBy { id.asc() } } }
}
val titles = loaded.flatMap { it.posts }.map { it.title }

val emails = db.user.projectMany { select { email } }.map { it.email }

val author = db.user.create {
    email = "author@example.org"
    posts.create { title = "First" }
}
db.user.count { where { posts { some { views gt 0 } } } }
```

Java: `q.include(i -> i.posts())`, `q.select(s -> s.email())`, `data.getPosts().create(post -> post.setTitle("First"))`.

## Загруженные поля

Чтение связи без include вызывает `VolanRelationNotLoadedException`. Загруженная nullable-связь может быть null, список — пустым. Это отличается от незагруженной связи. Проекция использует один сгенерированный `UserProjection`, а не отдельный класс для каждой комбинации колонок. Чтение пропущенной колонки вызывает `VolanFieldNotSelectedException`.

`select` и `include` задают разные формы результата; не объединяй проекцию и загрузку связей в одном запросе. Для HTTP явно создавай DTO: reflection-based сериализатор может обратиться к незагруженным getters.

## Число запросов

Loader собирает ключи родителей и читает связанные записи batches. Прямая связь использует один statement на batch ключей; неявная many-to-many дополнительно читает пары join table и затем целевые строки. Вложенные includes повторяют это для каждой запрошенной связи.

Это устраняет запрос на каждого родителя. Один дополнительный statement для любого размера результата не гарантируется: chunks ключей, ветви и глубина увеличивают число запросов. Текущий предел — 500 ключей родителей, дополнительно ограниченный числом параметров диалекта.

`take` / `skip` внутри include применяются к batch связанного запроса; не считай это контрактом top-N для каждого родителя. Ограничивай страницу родителей и запрашивай детей явно, когда нужен отдельный лимит на каждого.

## Фильтры и запись

Фильтры to-many: `some`, `every`, `none`; to-one: `matches` / `notMatches`. Они фильтруют строки, не загружая связи автоматически.

Вложенные операции `create` и `update` выполняются транзакционно; connect/disconnect и связанные записи доступны в поддерживаемых сгенерированных формах. Вложенность update глубже одного уровня связей и удаление owning-side required relation ограничены. Более глубокая запись должна знать остальные обязательные ключи. См. [Ограничения](/ru/limitations).

SQLite/MySQL/MariaDB требуют выбрать ровно distinct-колонки: `projectMany { select { email }; distinct { email } }` либо groupBy. PostgreSQL/H2 также поддерживают distinct с выбором представляющей строки.

## Пустая связь и незагруженная связь

Пользователь без публикаций получает пустой `posts`, если запрос включал эту связь. Если запрос не содержал include, чтение `posts` вызывает исключение. Это разные состояния: в первом случае база подтверждает отсутствие публикаций, во втором приложение вообще их не запрашивало.

У nullable to-one связи аналогичная разница между `null` и незагруженным свойством. Исключение помогает заметить, что код ответа требует данных, которых не было в запросе. Исправление находится на границе чтения: добавь нужный include либо измени DTO, чтобы оно не обращалось к этой связи.

## Фильтр родителей и фильтр детей

Условие `posts { some { views gt 0 } }` выбирает пользователей, у которых есть хотя бы одна подходящая публикация. Оно не означает, что все публикации пользователя будут загружены, и не ограничивает автоматически данные отдельного include. Условие внутри include, в свою очередь, управляет загружаемыми детьми и само по себе не заменяет фильтр пользователей.

Когда требуются «авторы с популярными публикациями и только эти публикации», это две части запроса: условие отбора авторов и условие загрузки публикаций. Опиши обе части явно. Для `every` учитывай смысл условия на пустом наборе: отсутствие детей не является доказательством существования подходящей публикации. Если наличие важно, выражай его через `some`.

## Как избежать неожиданного объёма

Batch loading убирает типичный цикл «один запрос на каждого пользователя», но большое дерево includes всё ещё может вернуть много строк. Ограничь страницу родителей, загружай только нужные ветви и измеряй количество statements. Если endpoint отвечает списком email, проекция проще и дешевле, чем чтение пользователей с публикациями.

Вложенный `posts.create` в примере создаёт автора и публикацию как связанную запись. Runtime передаёт ключ автора в запись публикации и выполняет операцию транзакционно. Внешние действия — например, уведомление о публикации — выполняй после успешного завершения транзакции.
