Бенчмарк помогает ответить на узкий вопрос: сколько времени занимает конкретная операция в заданной среде. Здесь измеряется чтение через пул PostgreSQL с материализацией полей. В опубликованном запуске Volan показал большее время, чем перечисленные альтернативы; цифры приведены без попытки скрыть это различие.

Эти результаты полезны как исходная точка для проверки и оптимизации. Они не описывают скорость любого приложения: размер результата, сеть, схема, includes и конкуренция меняют нагрузку.

| Library | 1 row, µs/op | 100 rows, µs/op |
|---|---:|---:|
| Volan | 2432.5 ± 76.7 | 2640.4 ± 145.4 |
| Hibernate | 1360.0 ± 171.6 | 1504.5 ± 163.3 |
| Exposed | 1791.6 ± 130.0 | 1816.3 ± 84.9 |
| jOOQ | 1233.7 ± 85.0 | 1458.8 ± 153.5 |
| JDBC | 1157.4 ± 44.5 | 1311.5 ± 86.4 |

Средние ± доверительный интервал JMH 99.9%, микросекунды на операцию; меньше — лучше. Замер 7 сентября 2026: Ryzen 5 5500, Windows 11, Corretto 25.0.3, PostgreSQL 17.10 в Docker/WSL2. 10 000 строк, четыре поля, один поток, HikariCP pool из четырёх соединений.

Операция включает создание запроса, получение соединения, read-committed транзакцию, материализацию полей и commit. Корректность проверяется до измерения. Случаи читают 1 или 100 строк через WHERE id >= ?, ORDER BY id, LIMIT ?. Настройки: 2 JVM forks, 3 × 2 с warmup, 5 × 2 с measurement, heap 512 MiB.

Suite не измеряет writes, includes, nested writes, конкурентный throughput, миграции, startup или allocations. Loopback networking входит в результат. Замеры не доказывают универсальную скорость или throughput приложения; сравнивай доверительные интервалы.

## Повторение

Нужны Java 17+ и Docker, для отчёта — Python. Из корня репозитория:

```bash
docker compose -p volan-bench -f benchmarks/compose.yaml up -d --wait
export VOLAN_BENCH_URL='jdbc:postgresql://localhost:55432/volan_bench'
./gradlew :benchmarks:jmh
python benchmarks/report.py benchmarks/build/results/jmh.json
docker compose -p volan-bench -f benchmarks/compose.yaml down
```

В PowerShell задай `$env:VOLAN_BENCH_URL = 'jdbc:postgresql://localhost:55432/volan_bench'` и используй `.\gradlew.bat`. Fixture создаёт собственную БД; не направляй её на данные приложения.

[Методика](https://github.com/thirtyeighttwentysix/volan/blob/main/benchmarks/README.md), [raw results и параметры машины](https://github.com/thirtyeighttwentysix/volan/tree/main/benchmarks/results).

## Как читать таблицу

Значение дано в микросекундах на операцию. Например, `2432.5 µs/op` — примерно `2.43 ms` для измеренного случая, а не время всех запросов Volan. Интервал рядом со средним показывает неопределённость этого замера; число без методики создаёт ложную точность.

Два столбца сравнивают чтение одной и ста строк. Они не позволяют вычислить линейную стоимость одной строки: в каждой операции есть постоянные расходы на соединение, транзакцию и сетевое взаимодействие. Сравнение выполняется для одинаковой определённой работы, не для произвольных возможностей каждой ORM.

## Измерение своего сценария

Если твоё приложение читает пользователя с несколькими связями, этот benchmark не покрывает такую нагрузку. Собери характерный запрос, зафиксируй объём данных, размер пула и concurrency, проверь корректность, затем измеряй. Отдельно наблюдай SQL statements и время ожидания соединения.

Не делай вывод только из первого запуска: прогрев JVM и базы влияет на результат. Сохраняй параметры машины и raw results, чтобы повторный замер можно было сравнить. Быстрый неправильный результат не является успешной оптимизацией.
